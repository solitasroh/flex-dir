# PRD — flex-dir v2 (계획)

> v1 은 끝났다 (2026-08-06). 이 문서는 **다음에 무엇을 만드나**가 아니라
> **무엇이 들어올 자격을 얻나**를 정한다. 이유는 §2 다.
>
> 확정 아님. `docs/PRD.md`(v1) 는 그대로 두고, v2 항목이 승격될 때마다 여기서 옮긴다.

## 1. v1 이 남긴 자리

v1 의 판정 기준은 **"하루치 작업 루프에서 기본 탐색기를 열 이유가 0인가"** 였다
(`PRD.md` §1). 기능이 전부 들어왔고 게이트 4종이 초록이지만, **그 질문의 답은 아직
모른다** — 도그푸딩 2일차였다 (당시 `scripts/check-dogfooding.ps1` 기준 지난 7일 중 2일).

> **그 세는 방식은 폐기됐다** (2026-08-07 · ADR-007 §폐기). 답을 얻는 방법이 "며칠 썼나"
> 에서 **"쓰다가 무엇에 걸렸나 — GitHub 이슈"** 로 바뀌었다. 아래 §3 이 세운 승격 조건은
> 그대로다.

**v2 계획의 첫 항목은 그 답을 얻는 것이다.** 답이 "탐색기를 아직 연다" 면, 왜 열었는지가
v2 의 내용을 정한다. 지금 목록을 확정하면 그 관측을 버리는 것이 된다.

## 2. 이 계획의 최대 위험 — 후보 목록이 전작의 실패 목록이다

| 전작이 **갖추고도** 실패한 것 (ADR-004) | v1 의 v2 후보 (`PRD.md` §3) |
|---|---|
| 탭 | v2+ |
| 4분할 | v2+ |
| 트리 | v2+ |
| 필터 | v2+ |
| 그룹핑 | v2+ |
| 자동업데이트 | v2+ |
| 세션복원 | **v1 이 이미 냈다** — 창 배치 · 마지막 폴더 · 폴더별 뷰 상태 |
| — | 네트워크 · 다크모드 (전작 목록에 없다) |

**후보 8개 중 6개가 전작이 만들고도 쓰이지 않은 바로 그 목록이다.**
ADR-004 가 적은 결론이 그것이다 — *"기능 부족은 원인이 아니었다."*

그러나 "그 목록에 있으면 금지" 는 규칙으로 틀렸다. **세션복원이 반례다** — 같은 목록에
있었지만 v1 이 냈고, 낸 이유는 그것이 v1 축(여러 폴더 왕복)에 직접 복무했기 때문이다.
매번 같은 두 폴더로 돌아오는 것이 이 앱의 존재 이유고, 복원이 없으면 그 왕복이 매일
처음부터다.

그러므로 판정은 목록이 아니라 **근거**로 한다.

## 3. 승격 규칙 — 후보는 증거로 들어온다

후보가 v2 범위에 들어오려면 **셋 다** 만족해야 한다.

1. **탈출구인가.** 그것이 없어서 **실제로 탐색기를 연 사건**이 있다. 기록이 근거다 —
   추측·"있으면 좋겠다" 는 근거가 아니다 (ADR-005 의 탈출구 봉쇄 논리 그대로).
2. **축에 복무하는가.** v1 축은 "여러 폴더 왕복" 하나였다 (ADR-004). v2 축은 §4.
   축과 무관한 것은 편의이고, 편의는 전작이 이미 증명한 실패 경로다.
3. **v1 이 성공한 축을 깨지 않는가.** 성능은 전작이 **유일하게 성공한 축**이다
   (ADR-016). 데이터 가상화·cold start·상주 프로세스를 깨는 방식이면 방식을 바꾸거나
   넣지 않는다.

> **3번이 그룹핑의 제외 사유였다** — *"전작에서 데이터 가상화를 깨뜨린 기능이다"*
> (`PRD.md` §3). 사유가 기능이 아니라 **구현 방식**을 가리킨다는 점이 중요하다. §6 참조.

## 4. v2 축 — 네트워크 하나

후보 중 **`PRD.md` §3 이 유일하게 `v2` 로 못박은 것**이다. 나머지는 전부 `v2+` —
v1 이 그때 이미 등급을 나눠 뒀다.

근거 셋:

- **ADR-007 이 이미 판정했다.** *"실행 가능한 게이트가 있던 항목(성능)만 성공했고,
  없던 셋(잔버그 · 조작감 · **네트워크**)은 전부 실패했다."* 네트워크는 전작이
  **갖추고도 안 쓴 기능이 아니라, 갖추지 못한 축**이다. §2 의 6개와 성질이 다르다.
- **탈출구다.** NAS 에 닿아야 하는 날은 flex-dir 로 하루를 못 난다. §3 의 1번을
  구조적으로 만족한다 — 관측을 기다릴 필요가 없는 유일한 후보다.
- **가장 값비싼 지식이 이미 문서에 있다.** `SHELL_NOTES.md` §네트워크 가 3주치 삽질의
  결론을 담고 있다 — `NetShareEnum` 이 아니라 `WNetOpenEnum`+`WNetEnumResource` ·
  오류 코드 8종의 경로/권한 분류 · 1219 함정. **다시 겪지 않아도 되는 상태다.**

### 4-1. 아키텍처 준비 상태 — v1 이 미리 열어 뒀다

| 자리 | 상태 |
|---|---|
| `Core/Locations/LocationId.cs` | `LocationKind` 에 `KnownFolder`·`ShellNamespace` 가 **v2 예약**으로 이미 있다 |
| 〃 | `LocationParseError.NetworkPath` — UNC 를 '잘못된 경로' 와 **구분해서** 거부한다. v2 가 이 분기를 살려 쓴다 |
| 〃 | UNC 판정을 구분자 정규화보다 **먼저** 한다 (함정 1). `\\?\UNC\server\share` 표현도 주석에 있다 |
| ADR-010 | 네트워크 v2 · 경로 추상화 v1 준비를 확정해 뒀다 |
| ADR-014 | PIDL 열거가 필요해지면 `IShellFolder::EnumObjects` 를 **따로** 세운다고 못박아 뒀다 |

**그러므로 v2 네트워크는 전면 수정이 아니라 확장이다** — ADR-010 이 노린 것이 정확히
이것이고, 그 도박이 성립했는지는 착수해 봐야 안다.

### 4-2. 네트워크가 건드릴 위험 지점

CLAUDE.md §3 이 여기서 시험받는다 — *"누가 얼마나 걸릴지 모르는 것이 기준이다."*

- **모든 저장소 호출이 초 단위로 늘어난다.** 열거 · `SHGetFileInfo` · 썸네일 ·
  `IFileOperation` 전부. UI 스레드 밖에 있는 것은 v1 에서 이미 지켰으므로 새로 만들 것은
  **취소와 시한**이지 스레딩이 아니다.
- **`IFolderWatcher` 가 SMB 에서 다르게 동작한다.** `FileSystemWatcher` 는 UNC 에서
  버퍼 오버플로와 조용한 정지가 흔하다. ADR-011 의 자동 갱신 전제가 여기서 깨진다 —
  폴백(주기적 재열거)이 필요한지 실물로 판정한다.
- **오류를 뭉뚱그리면 사용자가 손쓸 방법이 없다** (`SHELL_NOTES.md`). 경로 문제와 인증
  문제의 분리가 v2 의 UX 핵심이고, 1219 는 안내 문구까지 필요하다.
- **자격증명.** v1 에 없는 개념이다. 넣을지, `net use` 를 사람이 하게 두고 오류만 잘
  안내할지 — **미결** (§8).

## 5. 진입 조건 — 폐기했다 (2026-08-07)

이 절은 원래 이랬다.

> ① 도그푸딩 게이트 PASS(5/7) → ② v1 결함 소진 → ③ 사람 확인 잔여 처리.
> ①이 먼저인 이유: v2 축을 네트워크로 고른 근거 자체가 도그푸딩에서 나와야 한다.

**교착이었다.** 사용자가 이렇게 말했다 (2026-08-07):

> 내가 매일 쓰기 위해서는 네트워크 경로에 대한 접근이 필요해. 네트워크 쪽에서 작업을 많이 하거든.

**게이트가 막고 있는 그것이 게이트를 통과하는 데 필요하다.** "5일을 쓰고 나서 판단한다" 는
그 5일을 쓸 수 없게 만드는 조건이었다.

동시에 이 말은 §3 승격 조건 1번(탈출구인가)의 **가장 강한 근거**다 — 추측이 아니라 쓰는
사람의 증언이고, 이 문서가 요구한 바로 그 종류의 근거다. **축 선택은 맞았고 순서가 틀렸다.**

**바뀐 조건**: 네트워크는 도그푸딩의 **결과가 아니라 전제**다. 지금 착수한다.
게이트(현재 3/7)는 계속 세되 네트워크 작업을 막는 데 쓰지 않는다.

> **일반화**: 게이트의 입력을 막는 기능은 게이트 뒤에 둘 수 없다. ADR-007 의 게이트는
> "쓸 수 있는데 안 쓰는 것" 을 잡는 도구이지 "못 쓰는 것" 을 잡는 도구가 아니다.

**매핑 드라이브는 이미 된다** (2026-08-07 실측). `LocationId` 가 막는 것은 `\\` 로 시작하는
UNC 표기뿐이고 드라이브 문자는 그냥 지난다 — `Z:\`(NAS 매핑)에서 열거·아이콘·여유 용량
(1,760.7 GB)이 전부 정상이고 열거가 185ms 였다. **막힌 것은 UNC 표기다**
(`\\10.10.10.23\공유` · `\\wsl$\Ubuntu`). 사용자에게는 그것이 막힌 것과 같다.

### 범위 — 전부 (사용자 결정 2026-08-07)

```
N-2  열거·조작이 UNC 에서 도는가        ✅ 2026-08-07 — 열거·아이콘·breadcrumb·여유 용량 ·
                                          감시(생성·300개 오버플로) · 조작 넷(이름변경·복사·이동·삭제)
N-3  \\server 공유 목록                 ✅ 2026-08-07 — 실물 30개
N-4  오류 분류 + 자격증명 안내          ✅ 2026-08-07 — CredentialConflict 분류 + net use 안내
```

**v2 축의 범위는 이것으로 닫혔다.** 남은 것은 사람 손이 필요한 확인 둘(연결 끊김 ·
느린 서버에서의 조작감)이고 `.harness/manual-plan.md` 에 있다.

### N-4 가 정한 것 (2026-08-07)

**1219 를 `AccessDenied` 에서 떼어냈다.** 분류를 늘릴지 문구만 늘릴지가 갈렸고 —
**분류를 늘렸다** (사용자 결정). 근거는 이 문서가 §4-2 에 적어 둔 것 그대로다:
*"오류를 뭉뚱그리면 사용자가 손쓸 방법이 없다."* `AccessDenied` 는 "비밀번호나 권한을
고치면 되는 것" 인데 1219 는 **고쳐도 안 된다** — 기존 세션을 끊는 것 말고 방법이 없다.

| 자리 | 하는 일 |
|---|---|
| `Core/Errors/LocationError.cs` | `LocationErrorKind.CredentialConflict` + 그 분류만 경로 대신 **명령**을 낸다 |
| `Core/Locations/LocationId.cs` | `Server` — 끊을 대상은 공유가 아니라 서버다. 문구가 문자열을 자르지 않게 여기서 낸다 |
| `Core/Errors/Win32ErrorMapping.cs` | 53·67·1219 를 넣었다. **실물에서 본 것만** — 나머지는 여전히 `Unknown` |
| `Shell/Enumeration/NetworkShareSource.cs` | 1219 → `CredentialConflict`. `Translate` 가 `internal` 이 돼 채점된다 |

문구: `다른 자격 증명으로 이미 연결돼 있습니다 — net use \\10.10.10.23 /delete 후 다시 여세요`

**명령은 번역하지 않는다.** `LocationErrorMessages` 는 "한국어만" 이 규칙이었고 그 규칙이
테스트로 서 있었는데, **명령은 산문이 아니라 사용자가 그대로 치는 원문**이라 경로와 같은
취급이다 — 번역하면 붙여 넣어서 안 되는 명령이 된다. 예외가 그 하나뿐임을
`Describe_TheOnlyEnglishIsACommandToType` 이 고정한다.

**v1 이 남긴 유보를 여기서 풀었다.** `Win32ErrorMapping` 은 네트워크 코드를 전부 `Unknown`
으로 두며 *"v2 에서 실물 검증 없이 옳다고 믿게 된다"* 고 적어 뒀다. 그 기준을 그대로
이어받아 **실측한 셋만** 넣었다 — 53(없는 서버 · **42초 걸려 온다**) · 67(없는 공유) ·
1219(`net use` 로 확인). 1326·1311·1231·1232 는 이 경로(`FindFirstFileExW`)에서 오는 것을
아직 못 봐 `Unknown` 이다. 공유 열거(`WNet`)의 표와 다른 이유가 그것이다 — 같은 표 두 벌이
아니라 **다른 호출 경로**다.

### N-2 가 드러낸 것 — SMB 는 삭제 중인 폴더를 '액세스 거부' 로 낸다 (2026-08-07)

감시를 확인하려고 **보고 있는 폴더를 서버에서 지웠더니** 목록은 비워졌는데 사유가
`액세스가 거부되었습니다` 였다. 거짓말이고, `NotFound` 가 아니므로 상위로 올라가지도
않아(`PRD.md` §4) **빈 목록과 틀린 사유 앞에 갇혔다.** 같은 것을 로컬에서 하면 상위 폴더로
올라간다 — **네트워크에서만 다르게 동작했다.**

실측으로 창을 쟀다: 삭제 후 **367ms 에 `UnauthorizedAccessException`(5)**, **414ms 에
`DirectoryNotFoundException`(3)**. SMB 는 서버가 삭제를 접수하고 끝내지 않은 동안
(delete-pending) 새로 여는 요청을 전부 5 로 튕긴다. 로컬 NTFS 에는 그 중간 상태가 없다.
**감시 알림에 곧장 재열거하는 우리가 정확히 그 50ms 창에 들어갔다.**

고친 방식은 **네트워크 경로의 권한 실패만 250ms 뒤 한 번 더 여는 것**이다
(`FileSystemFolderSource.ShouldRetryOpen`). 진짜 권한 오류는 다시 물어도 같은 답이라
정확도를 잃지 않고, 값은 실패 경로의 지연 하나다. **다른 실패는 다시 묻지 않는다** —
없는 서버는 한 번이 42초다. 실물에서 고쳐진 것을 확인했다.

> **일반화**: 로컬과 네트워크가 같은 코드를 지나도 **오류 코드의 시간적 모양이 다르다.**
> "무엇이 오는가" 뿐 아니라 **"언제 오는가"** 가 분류를 바꾼다.

N-1 을 먼저 둔 이유는 B-1 과 같다 — **화면 없이 전부 채점되고**, 그것 하나로 N-2 가
드러난다. 실제로 그랬다.

### N-1 이 드러낸 것 (2026-08-07)

**UNC 를 담자마자 나머지가 대부분 그냥 돌았다.** `\\10.10.10.23\11_연구개발부_…` 에서
열거 · 형식 아이콘 · breadcrumb(서버가 첫 칸) 이 전부 정상이다. ADR-010 이 건 도박 —
"경로 타입만 열어 두면 v2 는 확장이지 전면 수정이 아니다" — 가 성립했다.

**그러나 세 곳이 UNC 를 모르고 있었다.** 전부 "거부되니까 올 리 없다" 는 전제 위에 있었다.

| 자리 | 증상 |
|---|---|
| `FileSystemDriveSpace` | `DriveInfo` 는 드라이브 문자만 받는다. UNC 루트는 `ArgumentException` → "모른다" 로 접혀 **여유 용량이 조용히 사라졌다.** `GetDiskFreeSpaceEx` 로 간다 |
| `ShellClipboardBridge` | UNC 경로를 **읽지 못하는 경로로 버리고 있었다** — 탐색기에서 네트워크 파일을 복사해 오면 붙여넣기가 조용히 비었다 |
| `PaneViewModel` 오류 문구 | "네트워크 경로는 아직 지원하지 않습니다" 가 거짓이 됐다 |

**교훈**: 거부하던 것을 받아들이면, 그 거부에 기대던 자리가 전부 조용히 틀린다.
테스트 셋이 깨져서 알았다 — 그 셋이 UNC 를 "나쁜 입력" 의 예로 쓰고 있었다.

### N-3 이 확인한 것 (2026-08-07)

`SHELL_NOTES.md` 가 적어 둔 격차가 **이 NAS 에서 그대로 재현됐다.**

```
net view \\10.10.10.23          → 공유 목록이 나온다   (WNet · mpr.dll)
Win32_Share / NetShareEnum 계열 → 실패                (LANMAN 파이프)
```

그래서 `WNetOpenEnum`+`WNetEnumResource` 로 갔고, 실물에서 **공유 30개**가 나온다.
`$` 로 끝나는 관리 공유는 숨긴다.

**한 클래스에 두 기제를 섞지 않았다.** 공유 열거(`NetworkShareSource`)와 폴더 열거
(`FileSystemFolderSource`)는 취소·오류·페이징이 전부 다르다. `RoutingFolderSource` 가
`LocationId.IsNetworkServer` 하나로 가르고, **그 라우팅 규칙 자체가 채점된다** —
ADR-014 가 PIDL 열거에 대해 "따로 세운다" 고 정한 것과 같은 판단이다.

공유 항목에는 크기도 수정 시각도 없다. `0` 이나 `0001-01-01` 을 그리면 그것이 사실인
것처럼 보이므로 **빈 칸이 "모른다"** 다 (`TimestampFormatter` 가 그 규칙을 갖는다).

### 6-1. 그룹화 — 들어왔다 (2026-08-06)

> **구현됐다.** 근거와 기각한 대안은 **ADR-017** 이 정본이고, 아래는 그때 세운 논증을
> 그대로 둔 것이다. 진입점은 **컬럼 헤더 우클릭 → 분류 방법**, 기준은 없음·이름·크기·
> 유형·수정한 날짜 다섯. **헤더 접기까지 넣었고 접힌 그룹은 폴더별로 기억한다.**
>
> **게이트가 BLOCK(2/7)인 상태에서 사람 재량으로 진행했다** (사용자 결정 2026-08-06).
> ADR-007 의 게이트는 보고만 하고 강제는 사람이 한다 — 그 재량을 쓴 첫 사례다.
> §3 의 1번(탈출구) 근거는 도그푸딩 중 사용자가 직접 걸린 것이다.

#### 그때 세운 논증 — 제외 사유가 무효가 되는 이유

`PRD.md` §3 의 제외 사유는 *"전작에서 데이터 가상화를 깨뜨린 기능이다"* 다.
**기능이 아니라 구현 방식을 가리킨다** (§3 의 각주). 그리고 그 방식을 안 쓰는 길이
v1 에 이미 깔려 있다.

- **ADR-016 의 합성 행.** wrap 뷰 3종이 `VirtualizingStackPanel` 을 지키려고 쓰는
  바로 그 패턴이다. 헤더도 행이면 가상화가 산다.
- **WPF 내장 `GroupStyle` 은 쓰지 않는다.** 그쪽이 가상화를 깨는 길이고, 로직이 XAML 로
  새어 자동 채점을 벗어난다 (CLAUDE.md §5).
- **그룹 키를 정렬 1차 키로 앞세운다.** `FileItemComparer` 가 다중 키를 이미 받는다
  (`Core/Sorting/FileItemComparer.cs`). 유형별 그룹 + 크기순 = `[Type, Size]` 정렬이고,
  정렬된 목록을 훑다 키가 바뀌는 자리에 헤더를 낸다. **투영이 순수 함수라 전부 채점된다.**
- **꺼져 있으면 지금 경로 그대로.** ADR-016 이 Details 를 평평하게 둔 대가(10만 항목에
  래퍼 10만 개)를 켰을 때만 치른다.
- **저장 호환.** `JsonViewStateStore` 의 `FolderRecord(Mode, Sort)` 에 nullable 필드
  하나를 더하면 기존 파일이 그대로 읽힌다.

**따라서 §3 의 3번(성공한 축을 깨지 않는가)을 만족한다.**

#### 남은 확인 — 사람이 봐야 하는 것

실물로 확인했다 (2026-08-06 · `PrintWindow` 캡처 + 합성 클릭): 헤더가 그룹마다 하나씩
서고 · 접으면 항목이 사라지고 개수는 남고 · **헤더 클릭이 선택을 풀지 않는다**
(목록의 터널링 핸들러가 먼저 가져가던 자리 — ADR-017 대가 항목).

아직 사람이 봐야 하는 것: **대용량 폴더(10만+)에서 그룹 투영의 체감** — 투영은 O(n)
이고 접기마다 다시 만든다. 정렬과 같은 비용이지만 실측은 없다. `manual-plan.md` §v1.1 에 있다.

## 9. 인스톨러와 자동 업데이트 (2026-08-07)

**이 문서가 막아 뒀던 것을 사용자 지시로 들였다.** §8 의 근거는 "전작이 갖추고도 실패한
목록" 이었는데, 사용자가 배포 경로를 요구했다 — §5 의 네트워크와 같은 종류의 뒤집기다.
**규칙이 아니라 사람이 판정한다** (ADR-007 이 게이트에 대해 정한 것과 같다).

### 무엇을 골랐나 (사용자 결정 2026-08-07)

| 갈림 | 고른 것 | 근거 |
|---|---|---|
| 도구 | **Velopack** | 인스톨러와 자동 업데이트가 한 몸. **per-user 설치라 관리자 권한도 코드 서명도 필요 없다** |
| 배포처 | **GitHub Releases** | 저장소를 public 으로 전환했다 — private 이면 배포물에 PAT 를 실어야 한다 |
| 적용 시점 | **알리고 사용자가 고른다** | 상주 앱을 마음대로 재시작하지 않는다. 받기는 미리 끝내 "지금 설치" 가 곧바로 반영되게 한다 |

public 전환 전에 무엇이 공개되는지 실측했다: **비밀값은 없고**(`.env` 는 이력에 없다)
사내 NAS 주소 41곳과 공유 이름 4곳이 이력에 남아 있다. 사용자가 그대로 공개하기로 했다.

### 표면

| 자리 | 하는 일 |
|---|---|
| `Core/Updates/IUpdateSource.cs` | 확인 · 받기 · 적용 셋으로 쪼갠 포트. Core 는 Velopack 을 모른다 |
| `Shell/Updates/VelopackUpdateSource.cs` | `UpdateManager` 를 감싼다. **설치되지 않은 실행에서는 조용히 '없음'** |
| `App/ViewModels/UpdateViewModel.cs` | 받아 둔 뒤에만 알린다. **실패는 조용하다** |
| `App/Views/MainWindow.xaml` | 상태표시줄 위 알림 바 (`지금 설치` · `나중에`) |
| `scripts/pack.ps1` | publish → `vpk pack` → `gh release` |
| `Directory.Build.props` | `<Version>` 이 배포 버전의 정본이다 |

### 값을 치르고 배운 것

1. **`UpdateManager` 를 생성자에서 만들면 앱이 안 뜬다.** 그 생성자는
   `VelopackApp.Build().Run()` 이 세우는 locator 를 요구해서, 부트스트랩 전이면 던진다 —
   테스트 실행기와 `dotnet run` 이 정확히 그 상태다. **업데이트와 무관한 앱 전체가
   조립에서 막힌다.** 늦게 만들고 `VelopackLocator.IsCurrentSet` 을 먼저 본다.
2. **설치 폴더와 상태 폴더가 같았다.** Velopack 은 `%LOCALAPPDATA%\<packId>` 에 설치하는데
   `packId` 가 `flex-dir` 이라 예전 상태 폴더와 **정확히 같은 경로**였다. 첫 설치에서
   `usage.log` 가 `current\`·`packages\`·`Update.exe` 와 한 폴더에 섞인 것을 보고 알았고,
   **그 설치가 실제로 기존 도그푸딩 기록을 지웠다.** 상태를 `%APPDATA%\flex-dir` 로 옮겼다.
   → **사용자 데이터를 설치기가 관리하는 폴더에 두지 않는다.**
3. **인스톨러가 게이트와 도그푸딩의 교착을 풀었다.** 저장소 산출물로 띄우면 상주 앱이
   그것을 잠가 빌드가 깨졌는데, 설치본은 `%LOCALAPPDATA%` 에서 돈다 —
   **설치본을 켜 둔 채 게이트 4종이 전부 통과하는 것을 확인했다.**

### 실물 확인 (2026-08-07)

0.1.0 설치 → 0.1.1 릴리스 → 앱이 확인·다운로드 → **`새 버전 0.1.1 이 준비됐습니다.`**
알림 바 → `지금 설치` → 패키지가 `flex-dir-0.1.1-full.nupkg` 로 교체되고 앱이 다시 떴다.
시작 메뉴·바탕화면 바로가기도 만들어진다.

**`나중에` 도 봤다** (0.1.1 → 0.1.2, 2026-08-07). 알림 바가 접히고 버튼 둘이 사라진다.
**그런데 다음 실행에 다시 뜨지 않는다** — 문서와 `UpdateViewModel.Dismiss` 의 주석이
"다음 실행의 확인이 같은 버전을 다시 찾는다" 라고 적고 있었지만 그럴 수가 없다:
**받아 둔 패키지는 다음 실행의 `VelopackApp.Build().Run()` 이 시작 지점에서 적용한다.**
그 실행은 이미 새 버전이고 피드에는 더 새 것이 없다.

> **미루는 대상은 재시작이지 설치가 아니다.** 결정이 지키려던 것("상주 앱을 마음대로
> 재시작하지 않는다")은 그대로 지켜진다 — 사용자가 스스로 끄고 켤 때 갱신된다.
> 받기를 미리 끝내는 이상 이 모양이 강제된다: 받아 둔 것을 적용하지 않으려면 매 실행마다
> 되돌려야 하고, 그러면 "받아 두는" 것의 의미가 없다.

## 10. 폴더 트리 (2026-08-10)

**§8 이 막아 둔 것을 사용자 지시로 들였다 — 세 번째다.** 앞의 둘은 네트워크(§5)와 자동
업데이트(§9)였고, 트리는 §2 가 *"전작이 갖추고도 실패한 6개"* 로 분류한 목록에 있다.

**규칙이 아니라 사람이 판정한다** (ADR-007 이 게이트에 대해 정한 것과 같다).

### 아이콘은 셋으로 갈린다 (2026-08-10 · 사용자 요청)

| 무엇 | 글리프 | 왜 |
|---|---|---|
| 로컬 폴더·드라이브 | 폴더 | 기본 |
| 네트워크 (UNC · **매핑 드라이브**) | 네트워크 | **펼치는 값이 다르다** — 서버가 죽어 있으면 수십 초다 (§5 N-4). 무엇을 누르는지 알고 눌러야 한다 |
| 서버 (`\\10.10.10.23`) | 서버 | 그 아래가 폴더가 아니라 **공유 목록**이라 한 겹 더 다르다 |

**`Z:\` 가 네트워크라는 것은 경로가 말해 주지 않는다.** `LocationId.IsNetwork` 는 `\\`
표기만 보므로 매핑 드라이브에 로컬이라고 답하고, 그것이 틀린 답도 아니다 — 경로 형식은
정말 로컬이다. 그 사실을 아는 곳은 드라이브 목록(`DriveEntry.Server`)뿐이라 노드를
만드는 쪽이 실어 준다. 그리고 **자식에게 물려줘야 한다**: 안 그러면 `Z:\work` 한 단계만
내려가도 다시 로컬로 보인다.

> §5 가 적어 둔 *"매핑 드라이브는 v1 때부터 됐다 — 파서가 막은 것은 `\\` 표기뿐이고
> `Z:` 는 그냥 지났다"* 와 같은 성질이다. **경로 문자열은 네트워크 여부를 다 말하지 않는다.**

### 값을 치르고 배운 것

1. **더미 자식을 넣지 않았다.** 지연 로딩 트리가 확장 화살표를 그리려고 흔히 쓰는
   수법인데, 목록에 없는 가짜 항목이 섞이면 (CLAUDE.md §4) 선택과 키보드 이동이 그것을
   밟는다. 대신 노드의 `CanExpand` 를 View 가 보고, 그 값은 **열어 보기 전에는 참**이다 —
   하위 폴더 유무를 미리 알려면 트리에 선 모든 노드를 열어야 하고 그것이 §3 이 금지한
   호출이다. 탐색기도 같은 낙관을 쓴다.
2. **대가는 자동화다.** UIA 는 자식이 없는 동안 노드를 `LeafNode` 로 보고
   `ExpandCollapsePattern.Expand()` 를 받지 않는다 (2026-08-10 실측). 펼치기 확인은
   합성 클릭으로 했다. UIA 접근성은 ADR-016 이 v2 로 미뤄 둔 그대로다.
3. **`AutomationProperties.Name` 이 없으면 노드 이름이 클래스 이름이 된다.**
   헤더가 `TextBlock` 이라 자동으로 잡히지 않아 `FlexDir.App.ViewModels.TreeNodeViewModel`
   이 나왔다 — UIA 로 트리를 훑다가 발견했고 한 줄로 고쳤다.
4. **접기는 `Visibility` 로 안 된다.** 열이 남아 왼쪽에 빈 띠가 생기고, 그러면 되찾으려던
   가로 공간이 그대로 없다. 열 너비를 0 으로 만들어야 한다 (`TreeSync`).

드라이브 둘(`로컬 디스크 (C:)` · `11_연구개발부_스마트디 (Z:)`)과 서버(`\\10.10.10.23`)가

전체를 쓴다.

**아직 사람이 봐야 하는 것**: 폭 드래그와 접힘의 **왕복**. `PersistAsync` 는

### 10-1. '네트워크 위치 추가' 로 등록한 곳 (2026-08-10 · 사용자 지적)

**매핑 드라이브만 보면 닿지 못하는 서버가 있다.** 사용자가 물어서 드러났고, 이 기계에서
실측하니 등록된 넷 중 하나(`\\10.10.20.30`)가 **어느 드라이브 문자에도 없었다.**

Windows 는 그 마법사의 결과를 드라이브가 아니라 **바로가기 파일**로 저장한다.

```
%APPDATA%\Microsoft\Windows\Network Shortcuts\<등록한 이름>\target.lnk
```

그래서 `WNetGetConnection` 에 원리적으로 잡히지 않는다 — 세션도 드라이브 문자도 만들지
않기 때문이다. 읽는 기제가 아예 달라서 포트를 나눴다 (`INetworkPlaceList`), 공유 열거와
폴더 열거를 나눈 것과 같은 판단이다 (§5 N-3).

| 이 기계에 등록된 것 | 대상 |
|---|---|
| `16_공통자료실` | `\\10.10.10.23\16_공통자료실` |
| `DEV` | `\\10.10.20.30\rsj0811` ← **매핑에 없는 서버** |
| `dev-server` | `\\10.10.20.30\rsj0811\workspace\docker-imx6-zeus\work` ← **깊은 경로** |
| `NAS_HOME` | `\\10.10.10.23\home` |

**서버로 접지 않고 등록 이름 그대로 세운다** (사용자 결정). `dev-server` 가 그 이유를
말한다 — 공유 루트가 아니라 네 단계 깊은 폴더이고, 서버로 접으면 그것을 등록한 이유가
통째로 사라진다.

**`Resolve` 를 부르지 않는다.** `IShellLink::Resolve` 는 링크가 살아 있는지 확인하러
네트워크로 나가고, 죽은 서버 하나가 트리 전체를 붙잡는다 (CLAUDE.md §3).
`SLGP_RAWPATH` 로 저장된 문자열만 꺼내며, 닿을 수 있는지는 실제로 펼치거나 열 때 안다.
바로가기 폴더를 읽는 것 자체는 **로컬 파일 읽기**라 매핑 드라이브보다도 싸다.

**실물 확인** (2026-08-10): 넷이 등록 이름 그대로 맨 아래 서고, `dev-server` 를 고르니
활성 페인이 `\\10.10.20.30 > rsj0811 > workspace > docker-imx6-zeus > work` 로 갔다
(항목 26개 · 여유 74.1 GB). `NAS_HOME` 펼치기도 하위 폴더를 냈다.
**폴더 안의 `target.lnk` 만 본다** — 마법사가 만드는 모양이 그것이고 실물에서 본 것도
그것뿐이다. 다른 모양이 실제로 있는 것을 보면 그때 늘린다.

### shell 컨텍스트 메뉴에 우리 항목을 넣었다

**v1 이 하지 않기로 한 것을 사용자 지시로 뒤집었다.** `IContextMenuProvider` 의 사유는
*"조작이 전부 키보드 맵과 툴바에 있다"* 였는데, 즐겨찾기 추가는 폴더를 **가리키며** 하는
조작이라 그 목록에 들어가지 않는다.

`SHELL_NOTES.md` §컨텍스트 메뉴가 방법을 이미 적어 두고 있었다 — 몰라서 안 한 것이 아니다.

| 함정 | 지킨 방식 |
|---|---|
| 3 — verb ID 범위 | shell 은 `1~0x7FFF`, 우리 것은 `0x8000` 부터. `AppCommandOf` 가 그 경계를 판정하고 **그 판정이 채점된다** |
| 8 — 앱 항목은 미뤄서 처리 | `TrackPopupMenuEx` 가 낸 ID 가 우리 것이면 `InvokeCommand` 를 부르지 않고 **인덱스만 돌려준다**. 실행은 메뉴 루프가 완전히 풀린 뒤 호출자가 한다 |

포트가 `Task<int?>` 를 내게 됐다 — shell verb 의 결과는 여전히 묻지 않는다(파일시스템이
진실원천이다). 돌아오는 것은 **우리 항목의 인덱스**뿐이다.

`PaneViewModel` 은 트리를 모르므로 `PinRequested` 이벤트로 경로만 내보내고
`WorkspaceViewModel` 이 잇는다 — 페인 간 복사를 잇는 것과 같은 자리다.

**존재 확인의 함정**: 즐겨찾기에 넣기 전 `TryGetItemAsync` 로 폴더인지 확인하는데,
**드라이브 루트는 부모가 없어 '그 폴더의 항목' 으로 물을 수가 없다.** 루트는 늘 폴더이므로
물음 자체를 건너뛴다 — 테스트가 이것을 잡았다.

### 값을 치르고 배운 것 — `StaticResource` 는 앞만 본다

**우클릭 한 번에 프로세스가 죽었다** (2026-08-10, 두 번). 스택은 이렇게 나왔다.

```
InvalidOperationException: '{DependencyProperty.UnsetValue}' 은 'ContextMenu' 의 유효한 값이 아니다
  at ContextMenuService.GetContextMenu(DependencyObject)
```

원인은 메뉴 자체가 아니라 **리소스 정의 순서**였다. `TreeNodeItem` 스타일이
`{StaticResource TreeNodeMenu}` 를 Setter 값으로 쓰는데 그 메뉴가 **뒤에** 정의돼 있었다.
`StaticResource` 는 자기보다 앞선 정의만 찾고, **못 찾으면 예외가 아니라 조용히
`UnsetValue`** 를 돌려준다.

> **일반화**: 증상이 원인에서 멀다. 컴파일도 테스트 1,515개도 통과하고, 스택은
> `ContextMenuService` 를 가리키지 리소스 순서를 가리키지 않는다. 터지는 시점은
> **처음 우클릭할 때**다. XAML 리소스는 위에서 아래로 해석된다는 것을 잊으면
> 이 자리를 다시 밟는다.

첫 진단은 `x:Shared="False"` 였고 **틀렸다.** 그것을 지워도 같은 자리에서 같은 예외가 났다.

**곁에서 드러난 것**: 이 예외는 처리되지 않은 채 프로세스를 죽인다. 상주 앱(ADR-003)인데
UI 스레드의 예외 하나가 트레이 아이콘까지 통째로 날린다 —
`Application.DispatcherUnhandledException` 핸들러가 없다. 이번 범위 밖이라 손대지 않았다.

> **→ §14 에서 닫혔다** (2026-08-11 · v0.4.2). 위 문단은 2026-08-10 의 사실로 남긴다 —
> **지금은 핸들러가 있다.** 여기만 읽고 "핸들러가 없다" 로 판단하지 않는다.

### 10-3. 트리가 페인을 따라간다 (2026-08-10 · 사용자 요청)

**§10 이 반대로 정해 둔 것을 뒤집었다.** 그 표의 *"페인이 움직이면 → 트리는 따라가지
않는다"* 는 같은 날 아침의 사용자 결정이었고, 근거는 *"경로를 따라 노드를 여는 것이 전부
저장소 호출이다"* 였다. **근거는 그대로 유효하다** — 그래서 뒤집으면서 값을 아낀다.

| 갈림 | 고른 것 | 근거 |
|---|---|---|
| 언제 | **활성 페인이 폴더를 옮길 때마다** | 탐색기와 같다. "목록에 포커스가 갈 때만" 은 이미 포커스가 있는 채로 더블클릭해 들어가면 따라오지 않는다 |
| 어디까지 | **경로 전체를 펼쳐 그 폴더까지** | 이미 펼친 범위 안에서만 고르면, 트리를 펼쳐 두지 않은 사람에게는 아무 일도 일어나지 않아 '안 되는 것' 으로 보인다 |
| 비용 | 가장 가까운 루트에서 출발 · 이미 연 단계는 다시 읽지 않음 · 새 탐색이 앞선 것을 끊음 | 즐겨찾기 `C:\Users` 가 있으면 드라이브에서 가는 것보다 한 단계 적다. 그 차이가 그대로 저장소 호출 수다 |

| 자리 | 하는 일 |

### 화면이 따라오지 않았다 — 가상화의 대가 (실물에서만 드러났다)

배선을 끝내고 실물을 보니 **노드는 펴졌는데 화면은 그대로였다.** 두 가지가 겹쳐 있었다.

1. **`TreeView` 는 프로그램이 정한 선택으로 스크롤하지 않는다.** 사용자가 클릭한 선택만

2. **화면 밖 노드는 컨테이너가 아예 없다.** 트리는 가상화돼 있고(같은 §5) 컨테이너는

   화면 밖이었고, 단순한 `BringIntoView()` 는 부를 대상조차 없었다.

> **얕은 경로에서는 멀쩡히 동작해서 더 늦게 드러났다.** `C:\Users` 도 `C:\Users\Public\Documents`
> 도 정상이었다 — 형제가 적어 컨테이너가 전부 실현돼 있었기 때문이다. **가상화 결함은
> 데이터가 작으면 보이지 않는다** (ADR-017 의 "항목 10개짜리 데모 폴더라 스크롤이 없었다" 와

고친 방식:

| 자리 | 하는 일 |

### 값을 치르고 배운 것 — 두 번 반대로 움직였다

**1. `GridSplitter` 는 언제나 두 열을 함께 조절한다.** `PreviousAndCurrent` 든 무엇이든

> 두고 남는 자리는 헤더 맨 뒤의 빈 열(`*`)이 먹는다.

**2. `DragDelta` 의 `HorizontalChange` 는 직전 이벤트 대비 증분이다.** 폭을 바꾸면 손잡이
자신이 따라 움직이고, 다음 증분이 그 이동을 상쇄하는 음수로 온다 — **끄는 방향과 반대로
밀린다.** 자기가 움직이는 손잡이에 증분 델타를 쓰면 반드시 생기는 되먹임이다.

> 고친 방식: `DragStarted` 에서 **시작 폭과 마우스 자리**를 기억하고, 매번
> `시작폭 + (지금 X − 시작 X)` 로 다시 계산한다. 헤더 `Grid` 는 움직이지 않으므로 그
> 기준계는 흔들리지 않는다.

> **일반화**: 컨트롤이 대신 해 주는 계산(두 열 배분 · 증분 델타)이 우리 모델과 다르면
> 그것을 쓰지 말고 **기준계를 직접 정한다.** 두 실패가 같은 뿌리였다.

**아직 사람이 봐야 하는 것은 없다** — 방향과 페인 독립을 사용자가 확인했다 (2026-08-10).
합성 드래그로는 확인하지 못했다: `Mouse.GetPosition` 이 `SetCursorPos` 로 옮긴 커서를
따라오지 않는다 (모달 드래그 루프 — `.harness/manual-plan.md` §확인 도구).

   두고 `CheckAsync` 가 그것을 부르며 결과를 버린다.
2. **`'설치되지 않음'` 을 말할 수 없다.** `IUpdateSource.CheckAsync` 는 개발 중 실행
   (`dotnet run`·빌드 산출물)에서도 `null` 이라 "최신" 과 구분되지 않는다 — 그래서
   저장소 빌드로 띄우면 '확인' 이 늘 **최신 버전입니다** 라고 답한다. 구분하려면 포트에
   '설치되었는가' 를 물어야 하는데 설정 창 하나 때문에 포트를 넓히지 않았다.
   **이 항목의 실물 확인은 설치본으로만 된다.**
3. **`Visibility` 를 `BooleanToVisibilityConverter` 로 낼 때 `FallbackValue` 가 없으면
   기본값이 `Visible` 이다.** 바인딩 원본(`Settings`)이 `null` 이면 변환기가 **아예 불리지
   않고** 대상 속성이 기본값으로 남는다 — 설정 없이 조립한 창이 설정 패널에 덮인다.
   업데이트 알림 바가 같은 모양인데 그쪽은 `Update` 가 늘 배선돼 있어 드러나지 않았다.
4. **설정을 바꿨을 때 트리를 `LoadAsync` 로 다시 세우면 안 된다.** 루트를 통째로 만들어
   펼쳐 둔 폴더가 전부 접힌다 — §10-2 가 즐겨찾기에서 배운 것과 같은 자리다.
   `ReloadFoldersAsync` 는 **이미 펼친 노드만** 다시 읽고 그 아래로 따라 내려간다.
   펼치지 않은 노드는 건드리지 않는다 (다음에 펼칠 때 새 정책으로 읽힌다).
5. **정책은 폴더를 열기 전에 서 있어야 한다.** `RestoreAsync` 가 설정을 먼저 읽고 페인·트리에
   민 뒤에 폴더를 연다. 순서를 뒤집으면 시작할 때 한 번은 옛 정책으로 그려지고 **아무도
   다시 읽지 않아** 숨김 항목이 그대로 남는다.
6. **숨김 필터를 지나는 자리가 둘이다** — 열거(`BuildRowsAsync`)와 감시 갱신(`ApplyAsync`).
   열거만 거르면 폴더에 숨김 파일이 **생기는 순간** 목록에 나타나고, 속성이 바뀌어 숨김이
   붙은 항목은 반대로 남는다. 둘 다 다음 새로 고침 때까지 간다.
   ADR-017 이 "목록의 원소 종류가 늘면 View 배선 셋을 함께 고친다" 로 배운 것과 같은 종류다.

## 13. 감시 오버플로 폭주 (2026-08-10 · 사용자 신고)

**`\wsl.localhost` 를 열었더니 목록이 끊임없이 갱신되고 선택이 먹히지 않았다.**

### 원인 — 처방이 증상을 다시 만든다

감시 오버플로(`FolderChange.Overflowed`)에 대한 처방은 **전체 새로고침**이다. 유실된 개별
변경을 흉내낼 수 없으므로 파일시스템을 다시 믿는다 (CLAUDE.md §4). 그런데 **그 새로고침이
감시를 다시 걸고, 다시 건 감시가 즉시 같은 오류를 낸다.**

```
WATCH full=True kinds=Overflow   ← FileSystemWatcher.Error
OPEN  \wsl.localhost\...\etc    ← 전체 새로고침 = 재열거 + 감시 재설치
WATCH full=True kinds=Overflow   ← 새 감시가 곧바로 또 Error
OPEN  ...                        ← 초당 약 10회, 영원히
```

**실측** (임시 계측 · 12초): 재열거 **123회** · 오버플로 **109회** · CPU **1.5코어** ·
UI Automation 읽기가 **120초를 넘겨 실패**(UI 스레드가 막혔다는 직접 증거다).

> **일반화**: 회복 동작이 자기가 회복하려던 조건을 다시 만들면 백오프 없이는 반드시
> 폭주한다. 처방과 증상이 한 고리에 있는지를 먼저 본다.

### 진단에서 무죄로 밝혀진 것 — 전부 실측했다

추측이 넷 다 틀렸다. 순서대로 재고 나서야 남은 하나가 드러났다.

| 의심 | 실측 결과 |
|---|---|
| `WNetEnumResource` 가 안 끝난다 | 배포판 셋을 내고 `ERROR_NO_MORE_ITEMS` 로 정상 종료 |
| 디렉터리 열거가 안 끝난다 / 중복을 낸다 | 2~180개 · 1~6ms · 중복 0 |
| 감시가 이벤트를 쏟아낸다 | 4초 동안 이벤트 0 · Error 0 |
| 64KB 버퍼가 네트워크에서 거부된다 | WSL·SMB·로컬 셋 다 Error 0 |
| 썸네일을 무한 재요청한다 | 항목당 250ms(로컬 78ms)로 느리긴 하나 `ThumbnailAttempted` 가 재시도를 막는다 |

**임시 계측이 결론을 냈다.** `OpenAsync` 와 `ApplyAsync` 에 한 줄씩 파일 로그를 넣자
고리가 그대로 찍혔다 — `perf.log` 로는 못 봤다: `FirstItemMeter` 는 **첫 항목만** 재므로
재열거를 세지 않는다. **계측이 있다고 해서 그것이 이 질문에 답하는 계측인 것은 아니다.**

### 고친 방식 — 늦추되 포기하지 않는다 (사용자 결정 2026-08-10)

| 갈림 | 고른 것 | 근거 |
|---|---|---|
| 폭주 처방 | **지수 백오프, 포기 없음** | 일시적인 문제면 저절로 회복한다. 상한(30초)이 있어 하루를 기다리는 상태가 되지 않는다 |
| 첫 오버플로 | **곧바로 새로고침** | 한 번은 정상이다 (파일 100개 복사면 그것만으로 넘친다). 늦추면 목록이 그만큼 오래 어긋난다 |
| 사용자에게 | **상태표시줄에 한 줄** | 목록이 파일시스템과 어긋날 수 있다는 것은 **손쓸 수 있는**(F5) 사실이다 — 업데이트 확인 실패를 조용히 두는 것과 다른 판단이다 |

| 자리 | 하는 일 |
|---|---|
| `Core/Watching/WatchBackoff.cs` | `Delay(연속 횟수)` · `IsConsecutive(간격)` · `IsThrottled`. 시각이 아니라 **간격**을 받아 순수 계산으로 남는다 |
| `App/ViewModels/PaneViewModel.cs` | `WaitOutOverflowAsync` · `IsWatchThrottled` · 상태표시줄 접미사 |

**실측 결과**: CPU **1.5코어 → 0.1코어** · UIA 읽기 **120초 초과 실패 → 4.1초** ·
상태표시줄에 `항목 180개 · 자동 갱신이 느려졌습니다 — 새로 고침(F5)`.

### 값을 치르고 배운 것 — 세는 값을 어디에 두는가

처음에 연속 횟수를 `WatchRun`(감시 하나)에 두었다. **그러면 영영 백오프가 걸리지 않는다** —
오버플로의 처방인 새로고침이 `WatchRun` 을 새로 만들기 때문에 세는 값이 매번 0 으로 돌아간다.
**세는 값은 그것을 리셋하는 동작보다 오래 살아야 한다.** 페인으로 옮기고 **폴더를 옮길
때만** 리셋한다.

> 재현 테스트가 이것을 잡았다 (`PaneWatchBackoffTests.RepeatedOverflows_TakeLongerEachTime` —
> 오버플로 3회가 101ms 만에 끝났다). 실물에서만 드러났으면 "고쳤는데 여전히 느리다" 가 됐다.

### 재현 테스트가 두 번 틀렸다 — 밀어 넣는 방식이 곧 재현이다

1. **한꺼번에 밀면 재현되지 않는다.** 감시 루프가 그것들을 한 배치로 묶어 `ApplyAsync` 를
   한 번만 지난다 — 세는 값이 1 에 머물러 백오프가 걸리지 않는다.
2. **재열거를 기다렸다가 다음 것을 밀어도 안 된다.** 재열거는 감시를 새로 걸고, **그 교체
   사이에 민 알림은 유실된다** — 기다리는 테스트는 거기서 멈춘다. 단독 실행은 통과하고
   전체 게이트에서 한 번 깨졌다.

지금은 `PushOverflowsAsync` 가 **120ms 마다 계속 민다** — 실물의 폭주 간격(100~200ms)과
같은 리듬이고, 하나가 유실돼도 다음이 온다. **실물의 감시도 우리 사정을 기다려 주지 않는다.**

> **일반화**: 폭주를 재는 테스트는 폭주의 *리듬*까지 흉내내야 한다. "몇 번 밀었나" 로
> 바꿔 넣으면 묶임과 유실이 조용히 결과를 바꾼다.

### WSL 경로 (2026-08-10)

`\wsl.localhost\<배포판>\...` UNC 로 **이미 된다** — 새로 만든 것이 없다.
`\wsl.localhost` 는 `LocationId.IsNetworkServer` 라 `NetworkShareSource` 로 라우팅되고,
`WNetOpenEnum` 이 배포판 목록을 낸다 (이 기계: `Ubuntu-26.04`·`rancher-desktop`·
`rancher-desktop-data`). `\wsl$\...` 는 이 기계에서 잡히지 않는다.

**남은 성질 하나**: shell 아이콘/썸네일 조회가 9P 경로에서 **항목당 250ms**(로컬 78ms)이고
결과는 `null` 이다. 폭주의 원인은 아니었지만 큰 폴더에서 아이콘이 늦게 붙는다.
지금은 손대지 않는다 (사용자 결정 2026-08-10: 여기서 멈춘다).

### 백오프만으로는 부족했다 — 깜박임이 남았다 (사용자 신고 2026-08-10 저녁)

**0.4.0 을 쓰면서 사용자가 다시 신고했다**: WSL 화면이 여전히 깜박이고 계속 갱신되는 것처럼
보이는데 로컬은 멀쩡하다. 백오프는 **초당 열 번을 30초에 한 번으로** 줄였을 뿐이고, 그 한
번이 하는 일은 그대로였다.

**그 한 번이 `ReplaceAll`·`SortItems` 를 지나 `Reset` 알림을 냈다.** ADR-011 이 *"그 Reset
알림이 WPF 목록의 선택을 날린다"* 를 배우고 **감시 갱신 경로만** `MergeItems` 로 고쳤는데,
그때 열거 경로는 **폴더 전환에서만 도는 코드**였고 거기서는 Reset 이 맞다. 감시 오버플로
폴백이 그 코드를 **같은 폴더에** 쓰기 시작하면서 전제가 조용히 깨졌다.

> **일반화**: "이 코드는 A 상황에서만 돈다" 는 전제 위에 최적화를 두면, 나중에 B 상황이 그
> 코드를 재사용할 때 **아무 경고 없이** 틀린다. 재사용한 쪽이 전제를 알 방법이 없다.

고친 방식 (`59c427d`): 같은 폴더를 다시 읽으면 배치를 모아 두었다가 끝에 한 번 `MergeItems`
로 병합한다. 바뀌지 않은 줄은 **인스턴스를 그대로 쓴다** — 새로 만들면
`ThumbnailAttempted` 가 함께 초기화돼 그 폴더의 아이콘을 전부 다시 묻고, 9P 에서는 그것이
항목당 250ms 다. 폴더를 옮길 때는 그대로 교체한다 (병합하면 두 폴더가 잠깐 섞인다).

**곁들여 수동 새로 고침(F5)도 같이 좋아졌다** — 지금까지 F5 마다 깜박이고 아이콘을 전부
다시 조회했다.

**실측** (저장소 Release 빌드 · `\\wsl.localhost\Ubuntu-26.04\etc`): 27초 동안 목록 컨테이너
재생성 **0회** (전에는 30초마다) · CPU **0.01코어**.

**곁에서 드러난 것 — 테스트가 알림 횟수에 기대고 있었다.** `PaneWatcherTests.WaitAsync` 의
판정식이 `Items` 를 열거하는데 갱신은 감시 스레드에서 온다. 갱신이 Reset 하나였을 때는 그
창이 좁아 드러나지 않았고, 개별 알림 여러 번이 되면서 `Collection was modified` 로 깨졌다
(`0378619`). 판정을 예외 안전하게 만들고 폴링을 덧붙였다 — **한 번 건너뛴 판정이 마지막
알림이었으면 다시 볼 기회가 없다.**

## 14. UI 스레드 예외 (2026-08-11 · 사용자 결정)

**우클릭 한 번에 프로세스가 죽었다** (2026-08-10 · §10-2 §값을 치르고 배운 것).
`Application.DispatcherUnhandledException` 핸들러가 없어서 UI 스레드 예외 하나가 그대로
프로세스를 끝냈다. 그때는 "이번 범위 밖" 으로 적어 두었고, 여기서 닫는다.

**상주 앱이라 값이 다르다** (ADR-003). 창 하나짜리 앱이면 예외에 죽는 것이 정직하다 —
사용자가 다시 켜면 된다. 여기서는 그 하나가 **트레이 아이콘과 상주 프로세스까지** 날린다.
사용자가 보는 것은 "우클릭했더니 앱이 사라졌다" 이고, cold start 를 아끼려고 상주를 고른
(ADR-003) 그 이득도 함께 사라진다.

### 갈림 셋 — 전부 사용자 결정 (2026-08-11)

| 갈림 | 고른 것 | 근거 |
|---|---|---|
| 무조건 삼키나 | **한도를 둔다** — 1분 안에 5회까지 | 아래 §폭주 |
| 어디로 말하나 | **알림 바** (상태표시줄 바로 위) | 업데이트 알림과 같은 어휘. 모달이 아니라 계속 쓸 수 있고, 창이 숨겨진 동안 난 사고는 바가 남아 있다가 다음에 창을 열 때 보인다 |
| 얼마나 드러내나 | **예외 이름까지** | 혼자 쓰는 도구이고 사용자가 개발자다. 익숙한 이름이면 그 한 줄로 다음 행동이 갈리고, 아니면 로그를 연다. 메시지 전문은 넣지 않는다 — 길이가 예외마다 달라 바가 목록을 밀어낸다 |

### 폭주 — 무조건 삼키면 §13 과 같은 고리가 된다

이 코드베이스에는 **매 프레임 도는 UI 핸들러**가 있다. `Views/VisibleRangeSync` 는
`LayoutUpdated` 하나에 걸려 있고 (§B-3 이 그것을 신호 하나로 모은 이유가 있다),
`FocusScroll`·`ListInput` 은 입력마다 돈다. 거기서 나는 예외를 전부 삼키면 앱이 죽는 대신
**초당 수십 번 예외를 내며 느려지는 좀비**가 된다 — 죽는 것보다 증상이 **더 안 보이는**
모양이다.

> §13 이 겪은 *"회복 동작이 자기가 회복하려던 조건을 다시 만든다"* 와 같은 종류다.
> 거기서는 백오프가 답이었고, 여기서는 **포기**가 답이다: 고칠 수 없는 고리라면 오늘처럼
> 죽는 편이 낫다. 그때까지의 기록은 이미 `error.log` 에 쌓였다.

`RecoveryWindow`(1분) 안에서 `MaxRecoveries`(5회)까지 살리고 넘으면 `Handled` 를 걸지
않는다. **창은 프로세스의 평생 예산이 아니다** — 상주 앱은 며칠씩 켜져 있고, 아침의 사고가
저녁의 한 번을 죽이면 안 된다. 그래서 마지막 시각 하나가 아니라 **각 사고의 시각**을 담는다:
"마지막 사고로부터 1분" 으로 재면 59초마다 한 번씩 터지는 폭주가 영원히 살아난다.

**예외의 종류는 가르지 않는다.** "이건 삼켜도 되고 저건 안 된다" 는 목록은 만드는 순간
틀리고 유지할 근거가 없다. 무엇이 왔는지는 로그가 말하고, 살릴지는 **얼마나 자주 오는가**
로만 정한다.

### 삼키면 진단 채널이 사라진다 — `error.log` 가 짝이다

2026-08-10 의 크래시를 진단할 수 있었던 **유일한 이유**는 처리되지 않은 예외가 Windows

## 15. 마우스 보조 버튼으로 뒤로·앞으로 (2026-08-11 · 사용자 요청)

| 이름 | `SingleInstanceGateTests.SendAsync_NoArguments_StillReachesThePrimary` |
|---|---|
| 증상 | `IOException: 파이프가 닫히는 중입니다` — `NamedPipeServerStream.WaitForConnectionAsync` |
| 실물에서의 뜻 | **두 번째 실행이 창을 못 띄운다.** 한 번 밟히면 되살릴 길은 재시작뿐이다 |

### 왜 인자 없는 두 번째 실행이 하필 그것을 밟나

두 번째 실행은 붙어서 인자를 쓰고 끊는다. **인자가 없으면 쓸 것이 없어 붙자마자 끊는다** —
`SendAsync([])` 가 가장 빠른 경로다. 그 순간 Windows 는 기다리던 서버를
**'파이프가 닫히는 중'(IOException)으로 깨운다.** 실패가 아니라 **이미 지나간 연결**인데
`ActivationsAsync` 가 그것을 그대로 던졌다.

### 왜 아무도 몰랐나 — 예외가 관찰되지 않는 자리였다

```
_ = router.RunAsync(gate.ActivationsAsync(lifetime.Token), lifetime.Token);   // Program.cs:125
```

**던진 예외가 아무 곳에도 닿지 않는다.** UI 스레드가 아니므로 §14 의
`DispatcherUnhandledException` 도 보지 못하고, `error.log` 에도 남지 않고, 알림 바도 뜨지
않는다. 앱은 계속 도는데 **활성화만 귀를 닫는다.**

> **소비자는 이미 옳았고 생산자가 그것을 깼다.** `ActivationRouter.RunAsync` 는
> *"활성화 하나 때문에 귀를 닫으면 그 뒤의 두 번째 실행이 전부 조용히 사라지고, 사용자에게는
> 앱이 죽은 것처럼 보인다"* 고 적고 처리 실패를 삼킨다. 그러나 **반복자 자체가 던지면**
> 그 `await foreach` 가 끝나므로 그 방어가 지나쳐진다. — **예외를 삼키는 자리는 루프
> 안쪽만으로 부족하다. 루프를 만드는 쪽도 같은 규칙을 져야 한다.**

### 고친 방식 — 빈 활성화로 낸다

`WaitForConnectionAsync`·읽기의 `IOException` 을 잡아 **빈 인자 활성화**로 낸다. 붙은 것은
사실이고 인자가 없는 연결의 뜻은 이미 정해져 있다 — **"창을 다오"**. 창을 한 번 보이는 쪽이
조용히 사라지는 것보다 낫고, 무엇보다 **반복자가 살아 있다.**

### 재현이 먼저였다 (`ActivationsAsync_ClientsThatConnectAndLeaveAtOnce_DoNotKillTheLoop`)

원래 테스트는 **12회 연속 초록**이라 그것으로는 못 잡는다 — 부하가 있어야 나는 경합이다.
붙고 곧 끊는 클라이언트를 **50번** 두들기면 결정적으로 난다. 값을 하나 배웠다:
**증상이 클라이언트 쪽 시한으로 먼저 보인다** — 서버가 죽은 뒤로는 아무도 붙지 못해
`ConnectAsync` 가 시한에 걸리고, 그러면 스택이 클라이언트를 가리켜 진짜 사유가 가려진다.
그래서 테스트가 `reading.IsFaulted` 를 먼저 보고 **서버 쪽 예외를 다시 던진다.**

고친 뒤 그 테스트가 10초 시한 대신 **36ms** 에 끝난다 (5회 반복 초록 · Host 92개 6회 초록).

### 소유 구조가 바뀐다 — 이것이 이 작업의 본체다

> ⚠ **이 절의 구조도는 §18(분할)이 뒤집었다** (2026-08-12). 아래 `LeftTabs`/`RightTabs`/
> `Left`/`Right`/`ActiveSide` 는 **더 이상 없다** — 페인은 1~4개이고 자리는 번호다.
> **현재 구조의 정본은 `docs/ARCHITECTURE.md` §4 다.** 이 절은 탭이 무엇을 왜 그렇게
> 만들었는지의 기록으로 남긴다 (2단 소유 구조와 그 이유는 §18 뒤에도 그대로다).

탭이 들어오기 전 `WorkspaceViewModel` 은 `PaneViewModel` **둘을 `readonly` 로** 쥐고,
`ActivePane` 이라는 파생 속성 하나로 모든 조작을 라우팅했다. 탭이 그 자리를 2단으로 만든다.

```
지금:  WorkspaceViewModel ──> PaneViewModel  ×2   (Left · Right)

이후:  WorkspaceViewModel ──> PaneTabsViewModel ×2   (LeftTabs · RightTabs)
                                    │
                                    ├─ Tabs: PaneViewModel ×N   (살아 있다)
                                    └─ Active: PaneViewModel     (이 중 하나)

       Left  == LeftTabs.Active     ← XAML 이 물고 있는 자리. 파생 속성으로 남는다
       Right == RightTabs.Active
```

**`ActivePane` 을 지나는 배선이 이미 일곱이다** — 트리 따라가기(양방향) · 즐겨찾기 고정 ·
설정의 시작 폴더 지정 · 페인 간 복사 · 이동 · 반대편 폴더 열기 · 마우스 뒤로/앞으로.
전부 "활성 페인의 활성 탭" 으로 한 단 깊어진다. **이 일곱이 자동 채점 대상이다.**

**조립은 이미 열려 있다.** `AppComposition.Create` 안에 `PaneViewModel Pane()` 지역 함수가
있어(포트 12개를 묶는다) 런타임에 페인을 더 만드는 길이 이미 나 있다 — `WorkspaceViewModel`
이 그 팩토리를 `Func<PaneViewModel>` 로 받으면 된다. **App 은 여전히 `Shell` 을 모른다**
(`CLAUDE.md` §1).

**정리 순서가 늘어난다.** `AppComposition.DisposeAsync` 가 지금은 `Left`·`Right` 둘을 접는데,
탭이 살아 있으므로 **모든 탭**을 접어야 한다. 순서 규칙(페인 먼저, shell 구현체 나중)은
그대로다 — 뒤집으면 진행 중인 썸네일 요청이 닫힌 STA 큐에 들어간다.

### 배경 탭은 감시를 놓는다 — §13 이 값을 치른 자리다

**활성 탭만 `IFolderWatcher` 를 든다.** 탭이 비활성이 되면 감시를 놓고, 다시 활성이 되면
**새로 고침 한 번**을 돌린 뒤 감시를 건다.

근거는 §13 전체다. 감시 오버플로 폭주는 이 저장소가 실물에서 값을 치른 사건이고, 처방
(백오프·재열거)이 증상을 다시 만드는 고리까지 밟았다. **탭 8개가 각자 감시하면 그 사건이
8배로 돌아온다** — 게다가 폭주한 탭이 화면에 없으면 `자동 갱신이 느려졌습니다` 문구조차
보이지 않는 자리에서 뜬다.

대가는 명시한다: **배경 탭은 외부 변경을 즉시 모른다.** 활성화 시점의 새로 고침이 그것을
메우고, 그때 선택은 유지된다 (`CLAUDE.md` §4 — 갱신 중에도 선택은 유지한다).

> **썸네일 스케줄러와 열거 세션은 탭마다 살아 있다.** 놓는 것은 감시 하나뿐이다. 썸네일은
> 화면 밖 탭에서 요청이 나가지 않으므로(`SetVisibleRange` 가 뷰포트로만 민다) 조용하고,
> 열거 세션은 폴더를 열고 나면 유휴다.

| 필드 | 담을 것 |
|---|---|
| 탭 하나 | 폴더 · 고정 여부 · 사용자 지정 제목(없으면 `null`) |
| 페인 하나 | 탭 목록(순서 그대로) · 활성 탭 번호 |

**기존 저장 파일과의 호환은 변환 한 줄이다** — 단수 필드는 "탭 1개짜리 목록" 으로 읽는다.
그 변환은 `JsonViewStateStore` 안에서 끝나고 ViewModel 은 모른다.

**시작 비용은 지금과 같다.** 배경 탭은 **위치만 들고 있다가 처음 활성화될 때 연다** —
시작할 때 열거가 나가는 것은 좌·우 활성 탭 둘뿐이다. cold start 는 전작이 유일하게 성공한
축이고(ADR-016) 여기서 깨면 §3 의 3번에 걸린다.

**저장 시점은 지금 그대로** — 종료할 때 한 번(`PersistAsync`). 탭이 늘었다고 매번 쓰지
않는다.

### 페인 간 이동이 가장 비싼 자리다

탭을 반대편 페인으로 끌면 **살아 있는 `PaneViewModel` 인스턴스의 소유권이 페인을 건너간다.**
지금 페인 간 드래그앤드롭은 **경로 문자열**만 싣는다 (`DESIGN.md` §9-1) — 성질이 다르다.

건널 때 함께 움직여야 하는 것: 감시 구독(활성이었다면) · 썸네일 스케줄러 · 열거 세션 ·
히스토리 · 선택. **인스턴스를 그대로 옮기면 전부 따라온다** — 그것이 옮기는 방식을
"새로 만들고 상태를 복사" 가 아니라 **"목록에서 빼서 반대편 목록에 넣는다"** 로 두는
근거다. 옮긴 탭이 도착한 페인에서 활성이 되면 그때 감시를 건다.

**메뉴가 먼저다.** 컨텍스트 메뉴 **'반대편 페인으로 보내기'** 가 소유권 이동을 완성하고,
드래그는 **그 위에 입력만 얹는다** (사용자 결정 2026-08-11: 둘 다 둔다). 순서가 이쪽인
이유는 둘이다 — 키보드로 닿는 길이 있어야 하고(`UI_GUIDE.md` 원칙 2), 어려운 절반(인스턴스
이동)이 드롭 대상 표시·피드백과 **분리되어 먼저 채점된다.**

**건너간 탭이 서는 자리와 그 뒤의 활성** (사용자 결정 2026-08-11 · 메뉴 경로에는 드롭 지점이
없어 정해야 한다):

| 갈림 | 결정 | 근거 |
|---|---|---|
| 도착 페인의 어느 자리 | **그 페인 활성 탭 바로 오른쪽**, 그리고 **그 페인의 활성 탭이 된다** | `Ctrl+T`·복제·되살리기와 같은 자리 규칙이 된다. 맨 뒤로 가면 탭이 많을 때 탭 줄 밖으로 나가 들어온 것이 보이지 않는다 |
| 활성 **페인** | **원래 페인에 머문다** | 보내는 것은 *"이건 저기 치워놨다"* 에 가까운 **정리 동작**이라, 연속으로 정리하려면 하던 페인에 남아야 한다. 되살리기(`Ctrl+Shift+T`)가 페인을 옮기는 것과 갈리는 지점이고 — 그쪽은 *"방금 그것을 원해서 누른 키"* 다 |
| 마지막 탭 | **보낼 수 없다** | 보내면 그 페인이 탭 0개가 된다. 마지막 탭이 닫히지 않는 것과 같은 규칙의 같은 이유다 (결정이 아니라 적용). **1분할이면 보낼 곳 자체가 없다** (§18) |
| 고정 탭 | **보낼 수 있다** | 고정은 *"닫히지 않는다"* 이지 *"움직이지 않는다"* 가 아니다. 고정 여부는 인스턴스에 붙어 있어 건너간 뒤에도 그대로다 |

**정책은 도착 페인 것으로 갈아입는다.** 컬럼 폭과 숨김 정책의 소유자는 페인이므로(아래
§렌즈 표) 건너온 탭도 그 페인의 값으로 그려야 한다 — 갈아입히지 않으면 건너온 탭 하나만
반대편 페인의 폭으로 남는다. 반면 히스토리·선택·열거 세션·썸네일 스케줄러는 인스턴스에
붙어 있어 **손대지 않아도** 따라온다.

**드래그 시작 자리로 구분한다.** 탭 줄에서 시작한 드래그는 탭 이동이고, 목록에서 시작한
것은 파일 드래그다. 두 개가 같은 화면에서 동시에 살아 있으므로 **탭 줄이 파일 드롭을 받는
자리인지**가 따라 나온다 — 받는다. 탭 위로 파일을 끌어가면 **그 탭의 폴더로** 떨어진다
(탐색기·브라우저 관례). 이것은 MVP 에 넣지 않는다 (아래 제외 목록).

### 자명하게 따라 나오는 것 (결정이 아니라 기존 규칙의 적용)

- **뷰 모드·정렬·그룹화는 탭이 갖지 않는다.** 폴더별 뷰 상태가 정본이므로
  (`FolderViewState`) 두 탭이 같은 폴더를 열면 같은 뷰다. 탭은 그 규칙을 바꾸지 않는다.
- **같은 폴더를 여러 탭에 열 수 있다.** 진입점이 넷이라 자주 생긴다. 막지 않는다.
- **탭 제목은 폴더 이름**이다. 드라이브 루트는 `C:\`, 네트워크 공유는 공유 이름. 사용자가
  바꿨으면 그것이 이긴다.
- **활성 탭이 바뀌면 트리가 따라간다.** `ActiveSide` 가 바뀔 때 이미 그렇게 한다
  (`WorkspaceViewModel.ActiveSide` → `RevealInTree`) — 탭 전환도 같은 자리를 지난다.
- **배경 탭의 폴더가 사라졌으면** 활성화되는 시점에 상위로 올라간다. 지금 페인 규칙 그대로다
  (`PRD.md` §4). 배경에서 미리 판정하지 않는다 — 그것이 저장소 호출이다.
- **페인 간 복사·이동·마우스 뒤로/앞으로의 대상**은 "그 페인의 활성 탭" 이다.

### 렌즈를 다시 통과시키며 잡은 것 (2026-08-11 · 기획 단계)

초안을 **사용자 렌즈 · 구조 렌즈 · 절제 렌즈**로 세 번 지나며 나온 것들이다. 셋 다 문서만
읽어서는 보이지 않고 **소유자를 따라가야** 나왔다.

| 렌즈 | 잡은 것 | 결정 |
|---|---|---|
| 구조 | **컬럼 폭이 탭마다 갈린다.** `PaneColumns` 는 `PaneViewModel` 소유이고 페인마다 따로인데(§11 · 사용자 지적 2026-08-10), 탭 하나가 인스턴스 하나면 탭 전환마다 컬럼이 튄다 | **페인의 모든 탭이 한 `PaneColumns` 를 공유한다.** 소유자를 `PaneTabsViewModel` 로 올리고 탭은 그것을 본다 — §11 이 "페인마다 따로" 로 정한 결론은 그대로 산다 |
| 구조 | **숨김 정책이 새 탭에 닿지 않는다.** `WorkspaceViewModel` 이 `Left`·`Right` **둘에** 밀고 있어서, 나중에 만든 탭은 기본값으로 뜬다 | 미는 대상이 `PaneTabsViewModel` 이 되고, **새 탭을 만들 때도 현재 정책을 실어 만든다** |
| 구조 | **감시 놓기/걸기가 겹친다.** 탭을 빠르게 오가면 이전 탭의 해제와 새 탭의 구독이 경합한다 | 전환마다 앞선 작업을 취소한다 — 트리 따라가기가 이미 그렇게 한다 (`FolderTreeViewModel.RevealAsync` §10-3) |
| 사용자 | **탭 전환 뒤 방향키가 안 듣는다.** 탭을 클릭하면 키보드 포커스가 탭에 남는다 | **전환 직후 포커스는 그 탭의 목록으로** 간다. 활성 페인 표시(§6)도 그 페인으로 옮겨간다 |
| 사용자 | **되살린 탭이 어디 갔는지 모른다.** 원래 페인의 원래 자리로 돌아가는데, 그 페인이 활성이 아니면 화면 밖에서 조용히 생긴다 | **되살린 탭이 활성이 되고 그 페인도 활성이 된다.** 방금 그것을 원해서 누른 키다 |
| 사용자 | **복제한 탭은 제목이 같다.** `Ctrl+T` 가 지금 폴더를 복제하므로 같은 이름 둘이 나란히 선다 | **새 탭은 활성 탭 바로 오른쪽에 서고 즉시 활성이 된다** (사용자 결정 2026-08-11). 제목이 같아도 방금 생긴 것이 어느 쪽인지 보이고, 원본으로 돌아가는 길이 바로 왼쪽이다 |
| 절제 | `Ctrl+PageUp/Down` 은 `Ctrl+Tab` 과 **완전히 중복**이다 | **남긴다.** 값이 `KeyBinding` 두 줄이고, 탐색기·브라우저가 둘 다 쓰므로 어느 손버릇으로 와도 닿는다 |
| 절제 | **페인 간 탭 드래그가 이 계획에서 가장 비싼 항목이다** (살아 있는 인스턴스의 소유권이 페인을 건넌다) | **드래그와 메뉴 둘 다 둔다** (사용자 결정 2026-08-11). 컨텍스트 메뉴 **'반대편 페인으로 보내기'** 가 소유권 이동을 먼저 세우고, 드래그는 그 위에 **입력만** 얹는다 — 키보드로도 닿아야 한다는 `UI_GUIDE.md` 원칙 2 가 메뉴 쪽을 필수로 만든다 |

### 값을 치르고 배운 것 (ViewModel·Core 구간 · 2026-08-11)

이 구간은 **화면 없이 채점되는 것 전부**다 — 소유 구조 · 저장 포맷 · 컨텍스트 메뉴 7개의
로직 · 페인 간 소유권 이동. 탭 줄 화면과 드래그는 다음 단계다 (ADR-009: 자동 채점되는
것만 자율 실행에 맡긴다).

**"그릴 순서" 를 ViewModel 이 내야 했다.** 고정이 목록 순서를 안 옮기기로 정하자
(위 §범위) 보이는 순서와 목록 순서가 갈렸고, 그 정렬을 XAML 에 두면 **자리를 판정하는
동작이 그것을 볼 수 없다.** 실제로 걸린 것은 `오른쪽 탭 닫기` 다 — 고정 탭을 우클릭하는
경우에만 둘이 갈리는데, 목록 기준으로 판정하면 **왼쪽에 그려진 탭이 "오른쪽" 으로 잡혀
함께 닫힌다.** 그래서 `StripTabs` 하나를 정본으로 두고 그리는 쪽과 판정하는 쪽이 같은
것을 본다.

**닫는 길이 다섯이라 되살리기의 입구는 하나여야 한다** — `Ctrl+W` · 가운데 버튼 ·
컨텍스트 메뉴의 닫기 셋. 각 경로가 스택에 직접 쌓는 구조로 두면 하나를 빼먹는 순간
**그 탭만 조용히 되살아나지 않고**, 어느 경로가 빠졌는지는 실물에서만 드러난다. 닫는
자리에서 `TabClosed` 하나를 쏘고 창이 그것만 듣는다.

**여러 개를 닫을 때는 오른쪽부터 닫는다.** 되살리기가 최근 것부터 꺼내므로 그 순서로
쌓이면 자리가 그대로 복원된다 — 왼쪽부터 닫아도 복원되기는 하지만, 기록되는 번호가 전부
같은 값이 되어 읽는 사람이 맞는지 확신할 수 없다.

**`Left`·`Right` 는 이름을 지켰다 — 타입만 뒤로 물러났다.** 기획은 *"`Left`/`Right` 를
`PaneTabsViewModel` 로 바꾼다"* 였는데 `MainWindow.xaml` 의 `ContentControl` 둘이
`Content="{Binding Left}"` 로 `PaneTemplate` 을 물고 있다. 타입을 바꾸면 그 템플릿 안의
바인딩 수십 개가 **컴파일 에러 없이 조용히 죽는다** — WPF 바인딩은 런타임 조회다. 그래서
`LeftTabs`/`RightTabs` 를 새로 두고 `Left`/`Right` 는 *"그 페인의 활성 탭"* 을 내는 파생
속성으로 남겼다 (사용자 결정 2026-08-11). **XAML 변경 0 으로 1단계가 끝났고 앱은 그 사이에도
지금처럼 돈다.** 탭 줄 단계에서 `LeftTabs.Tabs` 에 바인딩을 붙이면 된다.

**놓기는 취소하지 않는다.** 전환이 겹치면 앞선 작업을 취소하는데(구조 렌즈가 잡은 것),
취소가 **감시 놓기까지** 끊으면 버려진 전환이 감시를 든 탭을 배경에 남긴다 — 막으려던 §13
폭주가 화면 밖에서 도는 정확히 그 모양이다. `SuspendWatchAsync` 는 토큰을 받지 않고 항상
끝나며, 취소는 **뒤따르는 새로 고침만** 막는다. 탭을 겹쳐 오가는 테스트가 이것을 잡는다.

**`DisposeAsync` 에서 취소를 삼키지 않으면 STA 워커가 남는다.** 이 저장소의 관용구
(`catch (Exception error) when (error is not OperationCanceledException)`)를 그대로 옮겼더니
종료가 **자기가 방금 일으킨 취소**에 터졌고, `AppComposition` 이 shell 구현체를 닫기 전에
빠져나갔다. 상주 프로세스라 그것이 곧 스레드 누수다 (`FlexDir.Host.Tests` 가 잡았다).
관용구가 아니라 *"이 예외를 밖으로 내면 누가 무엇을 못 하게 되는가"* 를 물어야 하는 자리다.

**활성 탭은 번호가 아니라 인스턴스로 센다.** 저장 파일의 탭 경로 하나가 깨져 빠지면 그 뒤
탭들의 번호가 전부 하나씩 당겨지는데, 저장된 `activeIndex` 를 그대로 쓰면 **범위 안의 엉뚱한
탭**이 활성이 된다. 범위를 벗어나는 값과 달리 클램프가 잡아 주지 못한다 — 값이 유효해
보이기 때문이다. `JsonViewStateStore.ToTabs` 와 `PaneTabsViewModel.Capture` 가 같은 수를 쓴다.

**"기억이 없다" 와 "탭 0개" 는 다른 사건이다.** 탭이 전부 깨진 페인을 빈 목록으로 내면
복원이 그것을 *기억된 상태*로 받아 시작 폴더 규칙을 지나지 못하고, 페인이 빈 채로 뜬다.
저장소는 그때 `null` 을 낸다.

**닫은 탭은 기록만 남긴다** (사용자 결정 2026-08-11). 인스턴스를 살려 두면 ADR-018 이 대가로
적은 *"항목 수 × 탭 수"* 메모리에 닫힌 탭 10개만큼이 더 붙고, 그 탭들의 썸네일 스케줄러와
열거 세션이 종료 순서에 하나씩 얹힌다. 되살린 탭은 폴더를 다시 열고 히스토리·선택을
잃는다 — 브라우저도 그렇다.

**활성 탭을 닫으면 왼쪽으로 간다** (사용자 결정 2026-08-11). `Ctrl+T` 가 오른쪽에 세우므로
둘이 짝이다 — 잠깐 다녀온 탭을 닫으면 출발한 탭으로 돌아온다. 브라우저·탐색기는 오른쪽으로
가지만 그쪽은 새 탭이 맨 뒤에 서는 전제다.

**복제가 따라오는 것은 폴더뿐이다.** `Ctrl+T` 가 복제하는 것도 폴더이므로(위 §범위) 같은
규칙을 쓴다 — 고정과 사용자 제목까지 따라오면 같은 이름 둘이 나란히 서서 어느 쪽이 원본인지
알 수 없다. `Ctrl+T` 와 갈리는 점은 기준이 활성 탭이 아니라 **우클릭한 탭**이라는 것 하나다.

**이름을 다 지우면 폴더 이름으로 돌아간다.** `CustomTitle` 이 공백을 `null` 로 접는다 —
되돌릴 별도의 메뉴 항목을 두지 않기 위한 정규화이고, 접지 않으면 제목 없는 탭이 서서 어느
폴더인지 알 수 없다.

**아직 넣지 않은 것**: 탭 줄 화면 · 드래그(같은 페인 순서 · 페인 간) · 전환 직후 포커스
이전. 셋 다 사람이 판정하는 자리다 (`CLAUDE.md` §5).

### 값을 치르고 배운 것 (탭 줄 화면 구간 · 2026-08-11)

이 구간이 만든 것은 **탭 줄 XAML · 키 일곱 · 컨텍스트 메뉴 일곱 · View 배선 셋 · 드래그**다.
아래는 전부 **화면이 서야 드러난** 것들이라 앞 구간에서는 볼 수 없었다.

**`StripTabs` 규칙이 지키고 있던 것이 하나 더 있었다 — 스레드다.** 앞 구간은 그것을 *"그리는
쪽과 판정하는 쪽이 같은 것을 본다"* 로만 적었는데, 바인딩이 붙는 순간 두 번째 이유가 생겼다:
`CloseAsync`·`DetachAsync` 는 `await tab.SuspendWatchAsync()` 뒤에 목록을 건드리고 그
`SuspendWatchAsync` 는 `Task.Run` 이라 **항상 양보한다** — 즉 그 뒤는 UI 스레드가 아니다.
`StripTabs` 는 통째로 갈아 끼우는 평범한 리스트라 바인딩 엔진이 알림을 마샬링해 주지만,
`Tabs`(`ObservableCollection`)에 물렸다면 `CollectionView` 가 그 자리에서 던졌다.
**규칙 하나가 두 가지를 지키고 있었고, 둘째는 화면이 없을 때 보이지 않았다.**

**탭 줄은 탭보다 오래 살아야 한다.** 활성 탭이 바뀌면 `ContentControl` 이 무는
`PaneViewModel` 이 바뀌어 **페인 트리가 통째로 다시 선다.** 줄을 `PaneTemplate` 안에 두면
지금 누르고 있는 그것이 매 전환마다 새로 서고 가로 스크롤 위치와 드래그 상태가 함께 사라진다.
그래서 `ContentControl` 이 무는 것을 `Left` 에서 **`LeftTabs`** 로 올리고, 그 안쪽
`ContentControl` 이 활성 탭으로 `PaneTemplate` 을 다시 물렸다 — 앞 구간이 지킨 *"`Left` 의
타입을 바꾸지 않는다"* 는 그대로다. 바뀐 것은 **누가 무느냐**이지 템플릿의 계약이 아니다.

**`ScrollViewer` 를 쓸 수 없었다.** 가로 스크롤을 켠 `ScrollViewer` 는 내용을 **무한 폭**으로
측정하고, 그러면 *"180~90 사이 균등 분배"* 가 영원히 발동하지 않는다 — 패널이 자기에게 몇 px
이 주어졌는지 모르기 때문이다. 게다가 여기 필요한 스크롤은 스크롤바도 버튼도 없고 휠이
가로이며 활성 탭이 끌려오는 것이라 프레임워크에서 얻을 것이 거의 없었다.
`TabStripPanel` 이 오프셋을 직접 든다.

**`ItemsPanelTemplate` 안은 이름 범위가 따로다 — 그리고 `DataContext` 상속에 기대면 안 된다.**
두 번 걸렸다. (1) 삽입선을 줄 위에 얹은 `Canvas` 로 그리려 했는데 바깥에서 패널을
`ElementName` 으로 찾을 수 없어, 자리를 아는 유일한 곳인 **패널이 직접 그린다**(`OnRender`).
(2) `ActiveTab="{Binding Active}"` 가 그 안에서 조용히 `null` 이 됐다 — 조상을 명시해
고쳤고(`RelativeSource AncestorType=ItemsControl`), **증상이 "활성 탭이 스크롤로 안 끌려온다"
하나뿐이라 화면만 봐서는 원인이 보이지 않았다.**

**메뉴는 뜨고, 눌리고, 아무 일도 하지 않는다.** 컨텍스트 메뉴가 세 가지(그 탭 · 페인의 탭
목록 · 워크스페이스)를 다 잡아야 하는데 메뉴는 시각 트리 밖이라 손에 쥐는 것이
`PlacementTarget` 하나뿐이고, 그래서 `DataContext`·`Tag`·`Tag.Tag` 로 사슬을 만들었다 —
그리고 **그 마지막 고리(`ItemsControl.Tag`)를 묶는 것을 빠뜨렸다.** WPF 바인딩 실패는 예외를
내지 않고, `Command` 가 `null` 인 `MenuItem` 은 **정상으로 뜨고 `IsEnabled=true` 이며
눌리기까지 한다.** 메뉴가 뜨는 것을 확인한 것으로는 부족했다 — **일곱 개를 실제로 눌러
봐야** 드러났다. (`ARCHITECTURE.md` §5 의 "View 배선 셋" 과 같은 종류의 함정이고, 이번에는
자리가 메뉴였다.)

**재정렬에는 방향에 따라 갈리는 보정이 있다.** *"탭 1과 2 사이에 놓았다"* 를 그대로 자리
번호로 주면, 끌던 탭을 목록에서 빼는 순간 뒤가 한 칸 당겨져 **한 칸 더 오른쪽**에 선다.
앞으로 끌 때만 1을 빼고 뒤로 끌 때는 빼지 않는다(`TabDragInput.Target`). 자기 왼쪽 틈과
오른쪽 틈이 **둘 다 "안 움직인다"** 여야 하는 것도 같은 계산에서 나온다.

**탭 클릭의 활성 전환은 탭 전환보다 먼저 나가야 한다.** 순서가 반대면 새로 선 목록이
`Loaded` 시점에 *"나는 비활성 페인"* 으로 보여 포커스를 가져가지 않고, 증상은 **전환 직후
방향키가 안 듣는 것** — §17 이 사용자 렌즈로 잡아 둔 바로 그 고장이다. 그래서 활성 전환을
`Activate` 가 아니라 **`ActivateTab` 커맨드**에 두었다: `Activate` 는 `Receive` 도 지나는데
그쪽은 도착 페인이 활성이 되면 안 된다.

**우클릭은 탭을 활성으로 만들지 않는다 — 그래서 메뉴는 우클릭한 탭을 실어야 한다.**
`SendTabToOtherPane` 이 활성 탭만 보고 있어, 활성이 아닌 탭을 우클릭해 보내면 엉뚱한 것이
건너갔다. 매개변수를 받게 고쳤다(`null` 이면 활성 탭).

**"커맨드는 전부 있다" 가 사실이 아니었다.** 컨텍스트 메뉴 일곱 중 **이름 바꾸기**는
ViewModel 쪽이 *"`CustomTitle` 대입 하나"* 로 끝나 있다고 적혀 있었지만, 편집을 **여는·닫는
상태**가 없었다. `IsTitleEditing` 과 커맨드 셋을 더했고 편집기 자체는 목록·트리가 쓰던
`RenameEditor` 를 그대로 쓴다(`Subject` 에 한 줄).

**떼기와 받기의 짝이 두 곳에서 불리게 됐다** — 컨텍스트 메뉴와 드래그. 각자 순서를 쓰면
한쪽이 `DetachAsync` 의 `null`(마지막 탭)을 빠뜨리는 순간 그 탭이 **어느 페인에도 없는 채로**
사라진다. `PaneTabsViewModel.SendAsync` 하나로 묶었다.

**스펙에 없어 고른 것 둘** (실물에서 다시 봤고, 앞의 것은 2026-08-12 에 확정됐다):

- **탭 아이콘은 `E8B7`(폴더) 글리프다.** `DESIGN.md` §7 의 표에 탭 아이콘 항목이 없었다.
  shell 아이콘이 아니라 글리프인 이유는 `PaneViewModel` 이 폴더 아이콘을 내지 않기 때문이고,
  내게 하려면 그것이 저장소 호출이다.
  **사용자 결정 2026-08-12: 그대로 둔다. 그리고 `DESIGN.md` §7 에 등록했다** — 고른 값이
  스펙 밖에 남아 있으면 다음 사람이 근거 없이 바꾸거나, 바로 아래의 *"파일·폴더 아이콘은
  디자인 대상이 아니다"* 를 근거로 shell 아이콘으로 되돌린다. **그 되돌림이 배경 탭까지
  저장소 호출을 부른다** — 예외인 이유를 값 옆에 적어야 결정이 산다.
- **탭 컨텍스트 메뉴는 마우스 전용이다.** 탭은 `Focusable=False` 이므로(전환 직후 포커스가
  목록으로 가야 한다) `Shift+F10` 이 닿지 않는다. 이 앱에는 애초에 탭 줄로 가는 포커스
  순환이 없다(`Tab` 은 페인 전환이다).

**스펙의 근거가 무너진 자리를 실물이 곧바로 청구했다 — 활성 탭이 구분되지 않았다.**
`DESIGN.md` §1-1 은 활성 탭 배경이 `--pane-bg` 인 근거를 *"목록과 같은 색이라 아래로 이어져
보인다"* 로 적었는데, 페인 안 순서가 **탭 줄 → 툴바 → 주소줄 → 목록**이라 탭 아래에 오는
것은 목록이 아니라 툴바다. **이어붙일 대상이 없으니 그 색을 쓸 이유도 함께 사라졌는데 색만
남았고**, 남은 대비는 `--pane-bg`(`#FFFFFF`)와 활성 페인 줄 배경 `--chrome-bg`(`#F9F9F9`)의
**6/255** 뿐이었다. 스펙대로 넣었고 스펙이 틀렸다 — 사용자가 화면을 보고 그날 바로 잡았다.

고친 것: **활성 탭 위쪽 2px `--accent` 라인** (사용자 결정 2026-08-11). §6 이 활성 페인에
쓰는 관용구와 같은 것이고, 색 대비에 기대지 않아 다크 전환에도 살아남는다. 배경은 그대로
둔다 — 근거는 잃었지만 활성 탭이 밝은 쪽이라는 방향은 맞다. **비활성 탭도 라인 자리를 그대로
차지하고 색만 투명이다**: 아니면 전환할 때마다 글자가 2px 튄다.

> **일반화**: 근거가 무너진 값은 조용히 남는다. *"왜 이 색인가"* 가 *"아래 것과 같은 색이라"*
> 였는데 아래 것이 바뀌면 그 색은 이유 없는 값이 되고, **그래도 화면에는 그대로 그려진다.**
> 스펙을 옮겨 적을 때 값만 보고 근거를 안 보면 이 자리를 못 잡는다.

### 겹치는 자리를 적어 둔다 — 탭 고정 vs 즐겨찾기

**탭 고정(pin)과 즐겨찾기(§10-2)는 역할이 겹친다.** 둘 다 "자주 가는 폴더를 손 닿는 곳에"
다. 갈리는 점은 수명과 자리다 — 즐겨찾기는 트리에 영구히 남고 클릭하면 **활성 페인이
이동**하며, 고정 탭은 **그 페인에 열린 채로** 남는다.

이것을 결함이 아니라 **관측 대상**으로 둔다. 도그푸딩에서 한쪽만 쓰이면 다른 쪽을 덜어낼
근거가 생긴다.

`ListBox`·`TreeView` 를 거슬러 찾아 돌려주는데, 탭 줄은 목록의 **조상이 아니라 형제**라 그
탐색이 닿지 않는다. 창 단축키는 그대로 듣고 방향키만 한 번 먹통이 된다 — 클릭 한 번으로
풀린다. 고치려면 `RenameEditor` 가 페인 루트에서 목록을 **내려가며** 찾아야 하고
(`AddressFocus.AddressBoxIn` 과 같은 수), 그 값을 치를지는 실물에서 거슬리는지로 정한다.

**정해졌다 — 고치지 않는다** (사용자 결정 2026-08-12). 실물에서 밟아 보고 거슬리지 않는다고
판정했다. **판정 방법을 미리 정해 둔 것이 값을 했다**: *"거슬리면 고친다"* 를 남겨 두었기
때문에 이 자리가 *"언젠가 볼 것"* 으로 표류하지 않고 한 번에 닫혔다. 탭 제목 이름 바꾸기는
컨텍스트 메뉴로만 들어오는 드문 경로이고, 방향키가 클릭 한 번으로 풀린다.

## §18 분할 — 1~4 페인 (2026-08-12)

**사용자 지시로 들어왔다.** 이 저장소가 가장 오래 막아 두었던 항목이다 — `ADR-004` 가
*"전작은 4분할을 갖추고도 실패했다, 기능 부족은 원인이 아니었다"* 로 v2+ 에 미뤄 두었고,
§17 은 *"페인 접기(1분할)는 별개 기능이고 범위 밖"* 이라고 적었다. 탭이 지난 자리와 같다.

**§17 과 다른 점 하나**: 탭은 페인 **안**을 늘렸고, 분할은 페인 **자체**를 늘린다. 그래서
`PaneSide { Left, Right }` 열거형이 사라졌다 — 자리는 이제 번호다.

### 결정 일곱 (사용자 인터뷰 2026-08-12)

| 결정 | 고른 것 | 근거 |
|---|---|---|
| **배치** | **프리셋 네 단계** (1·2·3·4) | 재귀 분할 트리(tmux 식)는 저장 포맷·이웃 계산·전환 순서가 전부 트리 순회가 된다. 프리셋이면 저장할 것이 `PaneCount` + 비율 둘뿐이다 |
| **기본화면** | **1분할** | 매일 여는 화면이 한 칸이다. 다만 **기억이 없을 때**의 기본이고, 쓰던 사람은 저장 파일이 자기 분할을 들고 온다 |
| **'다른 페인'** | **직전에 활성이던 페인** (MRU) | 2분할에서는 그것이 정확히 예전의 "반대편" 이라 동작이 한 글자도 안 바뀐다. 3·4분할에서 비로소 갈리고, 그때 "방금 있던 곳" 이 왕복 작업의 실제 모양이다 |
| **조작** | 툴바 메뉴 · 탭 줄 우클릭 · **단축키 없음** | `Ctrl+1~4` 는 정렬 키가, `Ctrl+Shift+1~4` 는 보기 모드가 이미 쓴다 (`DESIGN.md` §9). 실제로 써 보고 고르기로 했다 |
| **새 페인의 폴더** | **기억된 자리 우선, 없으면 활성 페인 복제** | 빈 페인이 생기면 분할할 때마다 주소를 다시 쳐야 한다 |
| **분할 축소** | **접는다 — 닫지 않는다** | 다시 펴면 탭도 선택도 스크롤도 그대로다. 대가는 접힌 페인의 탭이 메모리에 남는 것이고, 그것은 ADR-018 이 이미 치른 값이다 |
| **슬롯 배치** | **자리가 안 옮겨가는 순서** | 아래 표 |

### 슬롯 배치 — 늘려도 열이 바뀌지 않는다

```
1분할        2분할        3분할        4분할
┌───────┐   ┌──┬──┐     ┌──┬──┐     ┌──┬──┐
│       │   │  │  │     │  │ 1│     │ 0│ 1│
│   0   │   │ 0│ 1│     │ 0├──┤     ├──┼──┤
│       │   │  │  │     │  │ 2│     │ 3│ 2│
└───────┘   └──┴──┘     └──┴──┘     └──┴──┘

1→2  0번이 좌로 좁아지고 1번이 우에 생긴다
2→3  1번이 위로 줄고 2번이 그 아래 생긴다   (0번은 그대로)
3→4  0번이 위로 줄고 3번이 그 아래 생긴다   (1·2번은 그대로)
```

**대가는 4분할의 3번이 좌하라는 것**이다 (읽기순서라면 우하다). 얻는 것은 **분할을 늘려도
보던 폴더가 화면 반대편으로 날아가지 않는 것**이고, 단축키가 없어 번호가 사용자에게
노출되지 않으므로 그 대가를 낼 자리가 없다. 노출되는 것은 `Tab`·`F6` 순환 순서뿐이고
그것은 시계 방향이다.

**가로 스플리터는 하나다.** 4분할에서 좌·우가 `RowRatio` 를 나눠 써야 격자의 가로줄이
일직선으로 이어진다. 3분할에서는 오른쪽 열에만 걸린다 — 왼쪽까지 걸치면 0번 페인 위에
끌 수 없는 띠가 생긴다.

### 저장 포맷 — 세 세대가 한 파일에 산다

`GlobalViewState` 가 `LeftTabs`/`RightTabs`/`LeftColumns`/`RightColumns` 넷을 버리고
`IReadOnlyList<PaneState>` 하나를 든다. 컬럼 폭이 탭 목록과 한 묶음이 된 것이 그 결과다 —
**페인이 생기고 사라지는 단위**가 곧 `PaneState` 다.

읽는 쪽(`JsonViewStateStore`)은 세 세대를 전부 안다:

| 파일 세대 | 필드 | 어떻게 읽히나 |
|---|---|---|
| v0.4 이전 | `leftFolder` · `rightFolder` | 탭 1개짜리 목록 → 페인 둘 |
| v0.5.0 | `leftTabs` · `rightTabs` · `leftColumns` · `rightColumns` | 페인 둘 |
| 지금 | `panes` · `paneCount` · `rowRatio` | 그대로 |

**`paneCount` 가 없으면 2 다.** 이 한 줄이 "이미 쓰던 사람은 2분할을 유지한다" 의 전부다 —
`GlobalViewState.Default` 는 1분할이지만 그것은 *기억이 없을 때*의 값이고, 저장 파일에 좌·우
탭이 있으면 그 사람은 2분할을 쓰던 사람이다. **옛 필드를 지우지 않는다**: 넷 다 지우면
v0.5.0 이하로 만든 파일이 기억을 통째로 잃는다.

**`Panes` 는 `PaneCount` 보다 길 수 있다** — 접힌 페인이 거기 남아야 재시작을 건너서도
"다시 펴면 그대로" 가 성립한다. 반대로 짧을 수도 있다 (4분할을 처음 켠 경우) — 모자란
자리는 활성 페인을 복제해 채운다.

**검증이 갈린다.** 비율(`SplitterRatio`·`RowRatio`)은 범위를 벗어나면 **던지고** 파일 전체가
기본값으로 접힌다 — 손상된 -3 이 0.3 이었는지 알 길이 없다. `PaneCount` 는 **자른다** —
5 에는 짐작할 수 있는 뜻이 있고(4), 그 하나 때문에 창 배치와 마지막 폴더까지 잃을 이유가
없다 (`PaneTabsState.ActiveIndex`·`TreeWidth` 와 같은 판단).

### 접기는 감시를 놓는다

`PaneTabsViewModel.SuspendAsync`/`ResumeAsync` 가 그 짝이다. 근거는 §13 전체다 — 감시
오버플로 폭주는 이 저장소가 실물에서 값을 치른 사건이고, **화면에 없는 페인이 감시를 들면
그 폭주가 보이지 않는 자리에서 돈다.** 게다가 상태표시줄 문구조차 못 보는 자리에서 뜬다.

같은 이유로 **접힌 채 복원되는 페인은 폴더를 열지 않는다** (`RestoreAsync` 의 `open`
매개변수). 폴더는 배경 탭과 같이 `PendingLocation` 으로 실리고, 펴는 순간 열린다 — 배경 탭이
처음 활성이 될 때와 **완전히 같은 길**이다 (`OpenAsync` 하나를 나눠 쓴다).

### 화면 — 판정만 채점한다

`Views/SplitLayout.cs` 의 `PlacementFor(count, part)` 가 순수 함수이고, 그것만
자동 채점된다 (`CLAUDE.md` §5 · `SplitterSync` 와 같은 모양). 격자는 **열 셋 · 행 셋으로
고정**이고 분할 수가 바뀌면 자식이 어느 칸을 차지하는가만 바뀐다 — 정의를 갈아 끼우면
그때마다 페인이 통째로 다시 그려져 스크롤과 선택 표시가 튄다.

**슬롯은 `Panes[n]` 이 아니라 속성 넷(`Pane0`~`Pane3`)으로 문다.** 인덱서 바인딩은 목록이
짧을 때 **조용히** 실패한다 — 컴파일러가 못 잡고 화면에서만 드러나는 자리이고, §17 이 값을
치르고 배운 것이 정확히 그것이다.

**`ResizeDirection` 을 명시한다.** 축이 둘인데 `Thumb.DragCompleted` 핸들러는 하나라,
스플리터가 스스로 축을 말하지 않으면 세로로 끈 것이 열 비율을 덮어쓰고 그 값은 저장
파일까지 간다 (§규칙 15 가 이미 지난 자리다).

안다 (§규칙 15 가 이 기계의 두 해상도를 경고한다). **한 번 밟아서 닫히는 종류가 아니라

### 아키텍처 — 브러시를 갈아 끼우지 않고 색만 바꾼다

**포트 하나가 늘었다 (16/16).** `ISystemThemeSource.ReadAsync` 가 OS 의
`AppsUseLightTheme` 레지스트리 값을 묻는다. `IDriveList` 와 같은 자리에 둔다 — COM 이
아니라 STA 도 정리도 필요 없지만, "누가 얼마나 걸릴지 모르는 것이 기준" (CLAUDE.md §3) 을
이 저장소의 다른 시스템 조회 포트와 똑같이 지키려고 비동기로 뒀다. 구현체는
`Shell/Settings/RegistrySystemThemeSource.cs`.

**`AppSettings.Theme`(`ThemeMode`)와 `ResolveIsDarkMode(bool)`가 Core 에 산다** — Host 와
`SettingsViewModel` 양쪽이 "지금 다크인가" 에 같은 답을 내야 해서다
(`ResolveStartFolder` 와 같은 이유).

**색을 입히는 방법이 이 구현의 핵심 결정이고, 여기서 값을 치렀다.**
`Views/ThemePalette.Apply` 가 리소스 사전의 16개 항목을 **새 `SolidColorBrush` 로 교체**하고,
`MainWindow.xaml` 의 브러시 참조 153곳이 `DynamicResource` 로 그것을 따라간다.

> ⚠ **처음에는 반대로 갔고 실물에서 뒤집혔다** (같은 날). `StaticResource` 를 그대로 두고
> 브러시의 `Color` 만 바꾸는 길이었고, 근거는 *"XAML 리소스는 자동으로 `Freeze()` 되지
> 않는다"* 였다 — **틀렸다.** BAML 로더는 정적 값만 가진 Freezable 을 freeze 하므로
> `Color` 에 쓰면 `InvalidOperationException` 이다. 게이트 4종을 통과하고(테스트가
> **코드로 만든** 브러시를 seed 로 썼다 — 그것은 frozen 이 아니다) 실물 첫 전환에서 터졌다.
> 전문과 일반화는 `ADR-020` §고친 것.

**루트 창의 `Background`·`Foreground` 도 같은 `DynamicResource` 다.** 그 둘은 원래부터
`StaticResource` 를 쓸 수 없었다 — `Window.Resources` 가 파싱되기 전에 창 자신의 속성이
파싱되기 때문이다(파서 순서). 결과적으로 지금은 브러시 참조 전체가 한 방식으로 통일됐다.

**OS 설정이 바뀌는 것은 `WM_SETTINGCHANGE`(`ImmersiveColorSet`) 로 온다.**
`Views/SystemThemeWatcher` 가 창에 훅을 걸고, 받으면 `SettingsViewModel.RefreshSystemTheme`
을 부른다 — 시스템 모드일 때만 화면이 따라가고, 라이트/다크로 고정한 사람은 OS 가 바뀌어도
그대로다.

### 실물 확인 (2026-08-12 · 저장소 Debug 빌드 · 4분할 상태)

**게이트 4종을 통과한 뒤 실물에서 결함 셋이 나왔다.** 셋 다 고쳐서 다시 확인했다.

| 확인 | 결과 |
|---|---|
| 다크 팔레트가 실제로 입혀진다 | ✅ 창 `#202020` · 목록 `#1F1F1F` · 크롬 `#2C2C2C` (`PrintWindow` 픽셀로 확인) |
| 테마 라디오 셋이 뜨고 즉시 전환된다 | ✅ 다크→라이트→시스템 왕복. **재시작 없이** 바뀐다 |
| `settings.json` 에 남고 재시작을 건너 산다 | ✅ `"theme": "Dark"` → 다시 켜면 다크로 뜬다 |
| 파일 이름 대비 | ✅ **고친 뒤**. 아래 §실물에서 나온 결함 셋 참조 |
| 스크롤바가 다크다 | ✅ 항목 91개 폴더에서 확인. 얇은 막대가 `--stroke-strong` 로 뜬다 |
| 툴바 드롭다운(우리 WPF 메뉴)이 다크다 | ✅ 배경 `#2C2C2C` · 흰 글자 · 체크 표시가 accent(`#4CC2FF`). 별도 팝업 창을 따로 찍어 확인했다 |
| 일반 창 크기에서도 정상 | ✅ 최대화를 풀고 확인 |
| `error.log` 가 깨끗하다 | ✅ 최종 상태에서 비어 있다 |

**실물에서 나온 결함 셋** — 전부 게이트 4종을 통과한 상태였다:

1. **`SystemThemeWatcher` 가 프로세스를 죽였다** (`AccessViolationException`). 훅이 **모든**
   창 메시지에서 `Marshal.PtrToStringUni(lParam)` 를 불렀고, `WM_SETTINGCHANGE` 가 아닌
   메시지의 `lParam` 은 문자열 포인터가 아니다. **`AccessViolationException` 은 §14 핸들러가
   못 잡는다**(corrupted state exception) — `error.log` 에도 안 남고 창이 뜨지도 않았다.
   이벤트 로그의 `.NET Runtime` 항목이 스택을 줬다. 지금은 판정 함수가 이름을 **지연 함수**로
   받아 메시지가 맞을 때만 읽고, 그 순서가 테스트에 드러난다.
2. **`JsonSettingsStore` 가 테마를 저장/복원하지 않았다.** 저장 형식이 Core 타입과 분리된
   자체 `Document` record 라서, `AppSettings` 에만 항목을 늘린 것으로는 아무 일도 일어나지
   않는다. 화면에서는 다크가 골라지는데 파일에 안 남고, 파일에 손으로 써도 안 읽혔다.
3. **다크 팔레트가 입혀지지 않았다** (frozen 브러시 — 위 §아키텍처 경고). §14 핸들러가
   예외를 삼켜 **화면만 조용히 라이트로** 남았다.

**그리고 다크가 라이트 시절의 잠재 결함 하나를 드러냈다.** `PaneList`(`ListBox`)에
`Foreground` 가 없어서 항목 텍스트가 WPF 시스템 기본색(검정 계열)을 상속하고 있었다 —
라이트에서는 우연히 맞아 **v1 부터 아무도 몰랐고**, 다크에서 파일 이름이 배경에 묻혀서야
보였다. 트리는 `TreeItemName` 이 이미 명시해 무사했다.

### 열린 것 — 아직 안 됨

- **OS 테마를 바꿔 시스템 추종을 밟지 않았다.** 이 기계 OS 가 라이트여서 "시스템 모드에서
  라이트로 뜨는 것" 까지만 봤다. 확인하려면 Windows 설정에서 라이트↔다크를 실제로 바꿔
  **앱이 재시작 없이 따라오는지** 보면 된다 (`WM_SETTINGCHANGE` 경로). 사용자 OS 설정을
  건드리는 확인이라 남겼다.
- **우클릭 컨텍스트 메뉴를 직접 밟지 않았다.** 같은 `MenuItem`·`ContextMenu` 템플릿을 쓰는
  툴바 드롭다운으로 간접 확인했다. **shell 컨텍스트 메뉴(목록 우클릭)는 OS 가 그리므로 우리
  제어 밖이고, 그것은 OS 테마를 따른다** — 앱을 다크로 두고 OS 를 라이트로 두면 그 메뉴만
  밝게 뜬다. 탐색기도 같은 자리다.
- **접근성 대비를 재지 않았다.** §값을 치르고 배운 것(활성 탭 배경색이 대비 6/255 였던
  사건)과 같은 함정이 다크에도 있을 수 있다. 눈으로는 읽히지만 수치로 재지 않았다.

## §20 툴바 오버플로와 알려진 폴더 (2026-08-21 · 사용자 결정)

**분할이 만든 자국이다.** 페인이 1~4분할이 되면서(ADR-019) 페인 하나의 폭이 최소 320px
까지 내려가는데, 툴바는 2분할 폭을 전제로 배치돼 있어 **좁은 페인에서 오른쪽 버튼들이
그냥 잘렸다.** 같은 구간에 알려진 폴더 드롭다운이 들어와 버튼이 하나 더 늘었으므로,
접힘 규칙과 새 버튼이 한 구간으로 묶였다. 구현의 정본은 `ADR-021`
(`Views/ToolbarOverflowPanel.cs`), 아이콘 판단의 정본은 `DESIGN.md` §7 이다.

### 접힘 규칙

**접기는 버튼 하나가 아니라 `FoldOrder` 무리 단위다** (ADR-021). 폭이 모자라면 번호가
작은 무리부터 통째로 접히고, 접힌 것이 하나라도 있으면 오른쪽 끝에 `»` 머리가 서서
같은 명령을 서브메뉴로 낸다.

| `FoldOrder` | 무리 | 접히는 순서 |
|---|---|---|
| 0 | 이동(`E72B`·`E72A`·`E74A`) · 새로 고침(`E72C`) · 알려진 폴더(`E707`) | **절대 안 접힌다** |
| 1 | *(비어 있다)* | 2구간의 외부 도구(`[VS]`·`[>_]`)를 위해 비워 뒀다 — 가장 먼저 접힐 자리다 |
| 2 | 분류 방법(`E8EC`) | 두 번째 |
| 3 | 뷰 모드 4종(`E8A4`·`E8FD`·`E8A9`·`E15B`) | 마지막 |

안 접히는 것의 기준은 **없으면 페인이 조작 불능이 되는가**다 — 이동과 새로 고침이 그것이고,
알려진 폴더는 이 구간이 들어온 이유라 접으면 본말이 뒤집힌다. 분류·뷰 모드는 접혀도
`»` 서브메뉴로 같은 일을 할 수 있다.

### 접힘은 언제 실제로 일어나는가 (실측 2026-08-21)

툴바 내용의 합은 **347px** 이다 — 버튼 32 × 10개(이동 셋 · 새로 고침 · 뷰 모드 넷 · 분류 · 📍) + 구분자 9 × 3개. `»` 머리가
32 이고 좌우 여백이 12 이므로 페인 폭으로 환산하면:

| 페인 폭 | 접히는 것 |
|---|---|
| ≥ 359 | 없음 |
| 350 ~ 358 | 분류만 |
| < 350 | 분류 + 뷰 모드 |

**4분할을 최대화해도 접히지 않는 것이 정상이다.** 4분할은 2×2 이므로(ADR-019) 1080 폭
모니터에서 페인 하나가 약 424 이고, 347 이 들어간다. **오버플로는 좁혀 보이게 하는 장치가
아니라 잘림을 막는 장치다** — 자리가 남는데 접으면 `»` 를 한 번 더 눌러야 하는 값만 치른다.

접힘을 실제로 보려면 창을 **`MinWidth` 900 언저리로 줄인 4분할**이어야 한다: 트리 220 +
스플리터를 빼면 페인이 334 이고 툴바에 322 가 남아 분류·뷰 모드가 함께 접히며, 이동 셋 ·
새로 고침 · 📍 가 남는다. **사람 확인은 그 상태로 한다** (사용자 확정 2026-08-21 — 임계값을
올려 넓은 페인에서도 접게 하는 안은 기각했다).

### 알려진 폴더 다섯

**홈 · 바탕화면 · 문서 · 다운로드 · 사진.** `E707` 드롭다운 하나로 낸다.

- **설정 없음.** 다섯은 고정이고 순서도 고정이다 (`IKnownFolderList` 의 `KnownFolderKind`
  순서). 목록을 편집하고 싶은 요구는 즐겨찾기(§10-2)가 이미 받는다.
- **경로가 빈 항목은 메뉴에서 뺀다.** 리디렉션·삭제로 실재하지 않는 폴더를 눌러 오류를
  보게 하지 않는다 — 다섯 자리 중 있는 것만 선다.
- **선택하면 현재 탭에서 이동한다.** 새 탭이 아니다. `NavigateAsync` 를 지나므로
  **뒤로가기에 쌓인다** — 눌러 보고 아니면 한 키로 돌아온다.
- **단축키 없음.** ADR-017 이 분류에 내린 것과 같은 판단이다 — 매일 누르는 조작이
  아닌 것에 키를 배정하면 그 키가 더 자주 눌리는 후보를 막는다.

### 항목 아이콘은 shell 에서 온다 (사용자 요청 2026-08-21 · v0.8.1)

**다섯 항목에 Windows 가 그 폴더에 붙여 둔 아이콘이 뜬다.** 다운로드의 화살표, 사진의
그림처럼 알려진 폴더는 저마다 다르다 — 같은 노란 폴더 다섯이 아니다.

**왜 새 포트가 아니라 `IThumbnailSource` 인가.** 기존 메서드 둘로는 안 됐다:
`GetThumbnailAsync` 는 `SIIGBF_THUMBNAILONLY` 라 폴더에서 언제나 `null` 이고,
`GetTypeIconAsync` 는 확장자 + `SHGFI_USEFILEATTRIBUTES` 라 **모든 폴더가 같은 아이콘**
이다. 그래서 `GetItemIconAsync`(경로를 보는 조회)가 늘었다. **`IKnownFolderList` 에 싣지
않은 이유**: 그러면 그쪽이 STA 워커와 `IDisposable` 을 들여야 하고(지금은 정리 목록에
없다), 이미지 리스트·BGRA 변환이 두 벌이 된다. *"어디에 있나"* 와 *"어떻게 생겼나"* 는
다른 포트다.

**비용은 다섯 번, 프로세스당 한 번, 배경 스레드다** (`knownFoldersAsked` 가드).
**경로를 보는 조회라 목록 항목마다 부르면 안 된다** — 대용량 폴더에서 확장자마다
한 번이라는 승리(§4)가 무너진다.

**아이콘 없이 먼저 뜬다.** 다 읽을 때까지 메뉴를 비워 두지 않는다 — 목록을 먼저 공지하고
아이콘을 채운 뒤 한 번 더 공지한다. 아이콘을 못 읽은 항목도 **목록에 남는다** — 거르는
기준은 경로 하나다 (위 §알려진 폴더 다섯).

**32 를 받아 16 에 그린다.** 150% 배율의 24px 메뉴 슬롯에서 16 원본은 뭉갠다.

### `E700` 이 아니라 `E707` 인 이유 (사용자 확정 2026-08-21)

햄버거(☰ `E700`)가 첫 후보였다. 둘이 기각했다: **`E700` 은 타이틀바의 폴더 트리 토글이
이미 쓰고 있다** — 4분할이면 같은 글리프가 한 창에 다섯 개가 된다. 그리고 ☰ 는
`DESIGN.md` §7 이 새 툴바 아이콘에 금지한 **선 계열**이다 (`E8A4`·`E8FD` 와 같은 실루엣).
`E707`(MapPin)은 물방울+원이라 어느 계열도 아니고, "위치로 간다" 는 뜻도 글리프에 있다.

### §값을 치르고 배운 것

**`Collapsed` 인 자식의 `DesiredSize` 는 0 이다.** 접은 버튼의 자연 폭을 다음 판정에서
다시 읽으면 0 이 와서 "자리가 남는다" 로 오판하고, 펼치면 다시 넘쳐 접는다 — **펼쳤다
접었다 진동한다.** 그래서 `ToolbarOverflowPanel` 은 접기 전 마지막 실측 폭을 캐시하고
판정은 언제나 그 값으로 한다 (ADR-021 §왜 캐시인가). 레이아웃을 조건으로 레이아웃을
바꾸는 자리는 **읽는 값이 자기 결정의 결과물인지**를 먼저 물어야 한다 — §17 의 "왕복이
고정점인가" 와 같은 계열이다.

**`MenuItem.Icon` 은 이 앱에서 그려지지 않는다** (v0.8.1 → v0.8.2 에서 값을 치렀다).
암시적 `MenuItem` 스타일(`MainWindow.xaml` §기본 항목 모양)의 템플릿에는 `Icon` 프리젠터가
없다 — 20px 0번 열은 **체크 표시(`E73E`) 자리**다. 그래서 `Icon` 에 무엇을 넣든
**예외도 경고도 없이 안 그려진다.** v0.8.1 은 그렇게 나갔고 메뉴가 글자만 뜬 채로 배포됐다.

찾는 데 세 번을 헛짚었다 — 리소스 위치(`Style.Resources` vs `Window.Resources`) ·
`x:Shared` · 데이터 유무를 차례로 의심했다. **셋 다 "컴파일되고 예외도 없으니 데이터나
바인딩이겠지" 라는 같은 전제에서 나왔다.** 갈라 준 것은 `Icon` 에 **리터럴 글자 하나**를
넣어 본 실험이었다: 그것마저 안 보이면 데이터도 바인딩도 아니고 **그리는 쪽에 구멍**이다.

> **규칙**: 안 보이는 것을 쫓을 때는 데이터를 의심하기 전에 **가장 단순한 상수**를 그
> 자리에 넣어 본다. 한 번의 빌드가 "안 오는가" 와 "안 그리는가" 를 가른다.

고친 방식은 **그 메뉴에만 `HeaderTemplate`** 을 주는 것이다. 전역 템플릿에 `Icon` 칸을
다는 안은 앱의 모든 메뉴(컨텍스트 메뉴 · 즐겨찾기 · 분류 · 분할)를 건드리므로 기각했다
(`CLAUDE.md` §2.3). **`Header` 를 세우지 않는 것이 핵심**이다 — 세우지 않아야 WPF 가 항목
자체를 `Header` 로 넣고, 그래야 템플릿 안에서 `Icon` 과 `Label` 을 둘 다 볼 수 있다.
`Label` 문자열을 `Header` 로 박으면 템플릿의 `DataContext` 가 그 문자열이 되어 `Icon` 이
사라진다.
